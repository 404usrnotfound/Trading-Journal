## Threat model and trust boundaries

Treat every broker file, mapping, filename, JSON field, query/header, financial identifier, note and attachment as untrusted. Threats include unauthenticated callers, malicious authenticated users, viewers trying to write, editors attacking another workspace or another member's browser, hostile web pages, malicious files and compromised dependencies. Browser-visible data, broker sources, credentials, sessions, private files, ledger integrity and service availability are protected assets.

HTTP callers cannot supply a trusted actor or authorization context. Server-verified database sessions determine the actor. Current workspace membership and role authorize each request and are rechecked inside the tenant transaction. Imported metadata never selects an SQL table, filesystem path, executable command or network destination. Broker parser code, operator provisioning/migrations, database administration, host filesystem ownership and deployment configuration are trusted administration boundaries. Compromise of those capabilities is outside this application-layer review.

The historical Phase 13 increment left financial domain behavior and the published migration chain unchanged. Later release remediation adds financial and security-reviewed migrations and application modules; consult the current migration journal and [audit remediation](audit-remediation.md). The shared database factory handles unexpected idle connection errors safely; ordinary query failures still reject. Validation precedes recursive parsing and private-file delivery; no financial assertion is replaced with a convenient zero.

Credential admission is defense in depth. The current Argon2id policy uses 32 MiB per hash; Node's default native worker pool already bounds simultaneous hashes, so default memory exhaustion was not confirmed. The explicit four-handler cap avoids application queuing and dependence on externally enlarged worker pools. Four simultaneous hashes at the current policy use approximately 128 MiB for hash work, excluding other application memory and trusted historical hash parameters. Excess credential requests receive `429` with `Retry-After: 1`; request validation runs before admission, while persisted login checks and credential handling share each admitted slot; capacity is released in `finally`. Controlled overlapping-handler tests verify the cap, mixed routes, errors/retries and session/logout availability without a real hash burst or OOM experiment.

The FA-03 remediation removes the aggregate `journal:login:ingress` window and disables only Better Auth’s redundant IP rule for `/sign-in/email`: the gateway deliberately replaces untrusted IP claims with a common loopback value, so that rule could otherwise reproduce the same all-user lockout. All other library rate rules stay enabled. The gateway keeps the existing ten-attempt fixed window for each normalized, HMAC-keyed email, with the same policy for provisioned and unknown identities and generic failures. Counter cleanup deletes at most 100 expired rows per admitted attempt. Login-counter allocation/checks and library credential work share the four-handler gate, so excess concurrent requests neither create identity buckets nor queue native work. Expired counters can be removed without erasing any active identity limit. Fresh identity rows can grow with admitted traffic during their fifteen-minute lifetime; capacity planning and trusted edge connection controls remain deployment responsibilities, rather than a persistent application-wide sign-in denial. Regression tests cover repeated/varied-email traffic, a valid unrelated user on a second gateway, existing legacy aggregate rows, identity-limit persistence/case normalization, bounded expiry cleanup, and excess-work rejection before database allocation.

The header policy is implemented in [browser-security.ts](../apps/web/src/lib/browser-security.ts) and [proxy.ts](../apps/web/src/proxy.ts); the proxy replaces forged policy/nonce headers and covers application documents and API paths. Every handler still authorizes separately. Core boundaries are [security.ts](../packages/server/src/security.ts), [auth-gateway.ts](../packages/server/src/auth-gateway.ts), [services.ts](../packages/server/src/services.ts), [private storage](../packages/server/src/storage.ts), [attachment validation](../packages/server/src/strategies/attachments.ts), [import parsing](../packages/server/src/imports/csv.ts) and [database tenant context](../packages/database/src/index.ts).

## Deployment obligations and remaining limits

- Terminate trusted HTTPS, configure the canonical APP_ORIGIN, preserve application security headers and deny framing on upstream error pages. HSTS does not provision TLS. Do not cache private HTML, RSC, API or file responses; keep public asset caching separate. Do not expose development tooling to untrusted networks.
- Keep runtime database roles least-privileged, migration credentials operator-only, private media outside public/build roots and host permissions restrictive. Encrypt and control backups/storage as appropriate; restore/rotation and production TLS/failover were not tested here.
- Add reviewed edge connection/body deadlines, per-tenant/concurrency/storage budgets and report throttling based on capacity. Never trust arbitrary X-Forwarded-For as a rate-limit identity. Monitor identity throttling and credential-capacity rejection without logging credentials or raw broker/journal input.
- Current uploads use format-envelope checks, not full decoding/AV. Canvas bounds do not bound animation frame counts or total decoder work. PDFs and raw evidence are untrusted when opened in external tools. Raster files beyond the new budget, including legacy files, are blocked without deleting or rewriting their history; forensic/operator recovery needs a safe out-of-band workflow.
- No active XSS, SQL-injection, path-traversal, SSRF or cross-tenant authorization exploit was confirmed in reviewed paths. This is not proof that future integrations, rich rendering, exports, infrastructure, dependencies or all browsers are secure. Keep regression tests and the dependency audit current, and perform deployment-specific review before public exposure.

The Phase 13 review itself did not perform a commit, push, merge or deployment. Later repository history and current release authorization are separate from that historical scope.
