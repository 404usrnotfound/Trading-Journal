# Private saved views and visible fields

Dashboard supporting trades, the trade journal list and the strategy list provide **Saved views and visible columns**. Select the optional table columns or list fields, then save column preferences. Trade/strategy identity remains visible so a row can always be identified and opened. Preferences load on a later visit; hiding a field does not alter its stored value, financial calculation or authorization.

A named view stores the current explicit filters for that screen. The dashboard saves its applied report scope, reporting currency, live/paper environment, source freshness, supplied-result selection, report tab, curve and supporting-trade search. Draft dashboard controls must be applied before saving a view. Journal views save title search, status, archived selection, account and local period choice/bounds. Strategy views save search, lifecycle status and archived selection. Relative journal periods such as Today or This week are recalculated in the workspace timezone when applied; explicit custom dates and dashboard dates remain the saved dates.

Choose a view and select **Apply saved view** to restore its filters. Saved views do not automatically replace incoming URL filters. Saving the same case-insensitive name replaces that named view with the current filter configuration; other names create additional views. A selected view can be deleted. Visible fields are a screen preference shared by its named filter views; this feature does not reorder columns, save arbitrary code or store financial report outputs.

These settings belong to one authenticated member in one workspace, including members with viewer access. Viewer access permits changing that member's own display preferences; it grants no journal, strategy or financial write permission. PostgreSQL's existing forced per-member preference RLS and membership foreign key protect the stored state. The API accepts no target user identifier, requires mutation-session/CSRF checks for writes and returns private, non-cacheable responses. Workspace portable archives exclude member preferences, preserving other members' private searches and view names.

Changes use an optimistic member preference revision and a transaction lock. Simultaneous or stale changes conflict and preserve the local column choices until explicit reload. A retry of the exact committed state returns the current result without another mutation. If a save response is lost or incomplete, editing pauses and the exact retained request must be retried. Other screens and the existing theme/timezone fields are preserved. Display writes record a generic audit action without private view names or filters, and do not advance the financial revision.

Each screen permits at most 20 named views, known columns and typed bounded filters. Duplicate identities/names, unknown fields, invalid statuses/dates and mismatched screen shapes are rejected. Write requests are limited to 64 KiB, with a 256 KiB database bound for the complete three-screen preference object. New financial selection fields can be optional for historical view compatibility; absent selections restore explicit empty defaults.

Focused verification lives in `tests/unit/display-views.test.ts`, `tests/integration/display-views.test.ts` and `tests/ui/display-views.test.tsx`. It covers typed validation, persistence after service/client recreation, same-workspace member and cross-workspace isolation, direct RLS visibility, private archive exclusion, concurrent/stale writes, CSRF, viewer-owned preferences, exact uncertain-save retries and all three screen configurations. Full browser/build checks and audit resolution are reviewed separately.
