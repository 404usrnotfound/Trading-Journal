## Preserve the database's responsibilities

The database contains application facts, authentication, queue state and migration history. The [schema composition](../../packages/database/src/schema.ts) links platform, financial, strategy, journal, accounting, import, reconciliation, risk, portability, period-review, supplied-value and outbox modules. Keep those boundaries intact in maintenance and backups.

- `app` holds tenant records, immutable financial sources/postings, versions, audit and controlled derived state. `auth` holds identities, password/session material, throttling and security audit. `queue` holds pg-boss runtime state and narrow native-snapshot functions. `migrations` holds the reviewed application migration journal.
- Authoritative source executions, postings, costs, source revisions, corrections, published strategies/original plans, journal revisions and import provenance are not disposable caches. Inventory books/positions/lots and native snapshots are controlled derived state, but that does not provide an operator license to clear/rebuild them with arbitrary SQL.
- Exact canonical source text and PostgreSQL numeric/time values must survive maintenance and recovery. The financial envelope is `NUMERIC(78,36)` with validation before coercion, not JavaScript floating-point conversion. Do not export/parse/rewrite all financial rows through a generic numeric transformation.
- Composite workspace references, forced RLS, immutable-history triggers and deferred conservation/revision checks complement application authorization. Keep owners, grants, policies, pinned function search paths and enabled triggers intact. A schema version marker alone does not prove those controls are intact.

The [core ledger](../core-ledger.md), [database implementation](../../packages/database/src/index.ts) and [financial migration](../../packages/database/migrations/0002_core_financial_ledger.sql) own these invariants. Correct financial evidence through guarded application commands with preserved provenance, not direct table updates or migration-journal edits.

## Maintain separate operator and runtime identities

| Identity / binding                            | Intended boundary                                                                                                                                                                                                                                                           |
| --------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Operator selected by `MIGRATION_DATABASE_URL` | One-shot reviewed application/queue migrations and runtime-role provisioning; never injected into a long-running web/worker process. The generated local operator is `postgres`; an external operator must meet the reviewed ownership/DDL/role requirements.               |
| `journal_migrator`                            | Non-login ownership identity with reviewed `BYPASSRLS`, `NOINHERIT`, no superuser/create-role/create-database/replication privilege. Owns protected application/auth objects and narrow privileged functions. It is not a runtime login or an inherited runtime membership. |
| `journal_app` / `DATABASE_URL`                | Authorized tenant application access, including tightly controlled mutable pointers/projections. It does not receive general authentication or queue-table access. Tenant context derives from a verified session inside the server transaction.                            |
| `journal_auth` / `AUTH_DATABASE_URL`          | Authentication-library tables and the allowed auth-security audit operations; not general tenant/queue access.                                                                                                                                                              |
| `journal_jobs` / `JOB_DATABASE_URL`           | Required queue DML/sequences and narrowly granted functions; not direct tenant/auth-table access or arbitrary queue DDL.                                                                                                                                                    |

Runtime identities must remain login-enabled, non-owner, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOBYPASSRLS`, `NOREPLICATION`, `NOINHERIT`, with no membership in another role. `NOINHERIT` alone does not prevent `SET ROLE`; the [production preflight](../../scripts/operations/production-preflight.ts) and [recovery role guard](../../scripts/operations/recovery-safety.ts) check that stronger boundary.

The [provisioning helper](../../packages/database/src/migrate.ts) reapplies explicit login/NOINHERIT/non-superuser/non-create/non-BYPASSRLS flags and configured passwords. It does **not** prove that an externally modified role lacks replication privilege, other memberships or ownership; preflight must still verify those facts. Do not treat rerunning provisioning as a universal role-repair tool. Investigate unexpected privilege changes under the security/incident process.

Queue grants are also restricted: `queue.version` and `queue.bam` are read-only except the required column-level update of `queue.version.flow_on`. The role can execute `queue.job_now()` and the reviewed claim/prepare/publish/fail native-outbox functions from [migration 0014](../../packages/database/migrations/0014_financial_outbox_dispatch.sql). These privileged functions mediate their precise projection scope; they are not broad tenant access. Provisioning applies default privileges for queue objects created by the reviewed owners without enabling arbitrary function execution.

### Coordinate credential changes

Changing a URL in `.env` does not change the PostgreSQL role password or an existing pool. The initializer preserves an existing `.env`; it is not a rotation command. There is no delivered automatic credential-rotation service.

1. Select the exact deployment/cluster and a maintenance/change window. Preserve working configuration in the approved secret-recovery channel and retain the required coordinated backup before schema/role repair or recovery. Record which web/worker instances use each identity without printing secrets.
2. Review the intended secret update and the existing migration prefix. The root `db:migrate` command includes application migrations, queue migrations **and all three runtime password/grant provisioning actions**; it is not a single-role password-only command. Follow [deployment](../deployment.md) for controlled invocation and complete-job serialization.
3. Apply the approved matching database/private-binding change through operator tooling. Provisioning takes generated passwords from private bindings and requires at least 24 characters; never place password-bearing SQL, URLs or secret arguments in a report or shell history. Its failure is deliberately sanitized.
4. Restart the affected supervised services with the matching bindings. Existing connections can outlive a password change, so an apparently working old pool is insufficient verification. Do not rotate the authentication signing secret merely to solve a database login failure.
5. Verify new connections for application, authentication and worker separately, the reviewed role/transport preflight, and an authorized representative read. Preserve role separation and wrong-workspace denial. Monitor safe error classifications after the change.

This is a coordination checklist, not evidence that production rotation was executed. Host secret delivery, rollback of a failed credential change and revocation timing require a deployment-specific rehearsal; use [verification](verification.md) for the actual local scope.

### Apply changes only through the release procedure

The [application runner](../../packages/database/src/migrate.ts) enforces PostgreSQL 17, acquires advisory lock `1791244800` with a 30-second lock timeout, checks applied hashes/timestamps/order against the exact reviewed prefix, applies reviewed SQL, and verifies the resulting schema. It rejects changed/missing/duplicate/unknown journal history before new application SQL. Historical migration integration tests also demonstrate rollback when a new constraint rejects an invalid historical identity rather than silently rewriting it.

The root [migration command](../../scripts/migrate.ts) then runs [pg-boss migration](../../apps/worker/src/migrate.ts) and role provisioning. Those stages are **not one atomic all-schema release transaction**, and the application advisory lock does not span the whole job. Serialize the complete deployment/recovery action and prevent old/new writers from acting across an unreviewed compatibility boundary. Keep traffic gated when a stage fails; preserve diagnostics and follow [database troubleshooting](../troubleshooting/database-and-migrations.md) before any retry.

Published SQL files and accepted snapshots stay unchanged. Add a reviewed forward migration for a new change; do not use schema `push`, run DDL automatically in replicas, edit hashes/version markers, disable triggers/RLS or execute a down migration against financial history. An additive filename is not proof that old/new releases can overlap. Code rollback requires explicit schema compatibility; recovering an older database loses later writes and is an intentional recovery decision. This repository provides no generic PostgreSQL major upgrade/downgrade or automatic down-migration procedure.

## Routine health and connection capacity

During an operator review, compare independent layers rather than treating one green probe as complete health:

1. Confirm release/private target and inspect database service status. A healthy local `pg_isready` means acceptance of connections, not correct passwords/schema.
2. Run the documented application-role readiness check, and inspect exact migration state when required. Authenticate through the normal browser boundary before testing protected web readiness.
3. Check authentication and worker separately. Web readiness checks tenant schema/major plus an auth query; worker readiness is its periodic infrastructure queue probe. Neither validates all financial facts, private media or every outbox item.
4. Review aggregate connection/activity counters, safe failure/time-out trends, database restarts, storage capacity and the age of verified coordinated backups. Use an approved monitoring identity; runtime tenant credentials are not a monitoring administrator.
5. If a check fails, follow the matching troubleshooting issue and collect a sanitized report. Restore dependency health before retrying uncertain writes; absence of a successful response/log does not prove the write did not commit.

The [shared pool factory](../../packages/database/src/index.ts) configures ten connections per web tenant pool and ten per auth pool, a five-second connection timeout, thirty-second idle timeout and ten-second statement timeout. Web receives a jobs URL for validation but opens no worker queue pool. The [runtime queue](../../apps/worker/src/queue.ts) caps each worker pool at four and uses five-second statement/lock bounds. These are source defaults, not exposed environment tuning knobs. See the existing [capacity budget](../operations.md#database-connections-and-capacity) for tooling/rollout headroom and the approved aggregate queries; do not duplicate or alter those query definitions here.

Budget simultaneous old/new replicas, backup/restore/migration/monitoring sessions and reserved administrator headroom against the real server limit. Increasing replicas, pool sizes or statement timeouts is not a demonstrated remedy for slow queries. Preserve bounded report scopes and the [performance evidence](../performance.md); production-scale FA-04 remains open. Do not kill unidentified sessions, expose SQL/parameter text, or weaken timeouts/security merely to make a probe pass.

## PostgreSQL maintenance responsibilities

The repository does **not** configure a production database-maintenance scheduler, autovacuum thresholds, VACUUM/REINDEX policy, physical replication, WAL archive/PITR service or automatic major upgrades. The local Compose file pins its PostgreSQL image and persistent development volume; that is not a production storage/maintenance plan. The worker sets pg-boss `reindex: false` and `monitorVacuum: false`; these queue-client options do not disable or replace PostgreSQL autovacuum.

**Operator recommendation, deployment-specific and Not run here:** retain an appropriate PostgreSQL 17 autovacuum/statistics policy and monitor table/index growth, dead tuples, vacuum/analyze progress, transaction-ID age, long-running/idle-in-transaction sessions, disk/WAL pressure and backup space. Review those facts with the database owner before selecting thresholds or maintenance windows. The repository's performance fixture runs `ANALYZE` on generated benchmark databases; that is not an installed routine maintenance job or evidence for a production cadence.

Maintenance that rewrites/reindexes objects, changes privileges/storage, removes retained data or upgrades PostgreSQL needs a separately reviewed plan, capacity/lock/outage assessment and a verified coordinated recovery set before potentially destructive work. Rehearse the exact supported operation on an isolated copy and verify application roles, migration history, constraints and representative financial/media reads afterward. This document intentionally supplies no generic VACUUM FULL, REINDEX, purge or session-termination command to run against user data.

Queue retention applies only within its configured job lifecycle. It does not authorize pruning financial sources, outbox intent, idempotent responses, original plans, audit, import evidence or private attachment references. Operational log retention and backup expiry are different policies from authoritative financial-history retention. No general user-data deletion/purge workflow is established by a database administrator's ability to issue SQL.

## Backup, maintenance and recovery verification

Before a schema/role repair, storage rewrite, destructive maintenance or recovery/cutover action, verify that the [coordinated backup procedure](../backup-and-recovery.md) has a successful recovery set and recoverable secrets. Database-only dumps cannot capture ongoing filesystem changes atomically; use the canonical write-quiescence boundary for web, worker and all other writers. Preserve complete app/auth/queue/migration data, owners/grants/functions/policies/sequence state and matching private media/release identity.

Restore to a new isolated target before cutover; do not delete an existing volume or run a destructive restore over the current database as a routine fix. Do not migrate an empty restore target first: a complete archive contains schema and journal state. Verify the same release's hashes/sequence/security fingerprints, authorized and denied reads, exact financial/report context, attachments and applicable queue/outbox recovery before opening writes. A portable single-workspace archive serves a different boundary and is not the full database/auth/queue/media disaster-recovery set.

The existing logical recovery drill has retained local evidence; [Checkpoint 4 verification](../troubleshooting/verification.md) freshly reproduced dependency-outage recovery and portable-archive checks on disposable resources; it did not rerun the SQL/media recovery drill. [This checkpoint's verification](verification.md) records any new execution rather than relabeling earlier timings as current or as production RPO/RTO. Backup scheduling/offsite durability, encryption/key recovery, PITR/media timestamp coordination, host failover and actual production maintenance remain external deployment responsibilities until separately exercised.
