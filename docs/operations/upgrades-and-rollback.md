# Upgrades and rollback decisions

Reviewed **26 October 2026** for Phase 19 Checkpoint 5 against Checkpoint 4 commit `b75b04cc92dbe89bb4bf131600fd1cb0a31a77e4`, with application baseline `5132900a03efabaeb307787531546987228220e7`. Audience: the release/database operator and incident owner. This guide owns upgrade sequencing, dependency-change decisions and the choice between retry, compatible code reversion and coordinated recovery. [Deployment](../deployment.md) owns release preparation, topology, configuration and launch commands; [backup and recovery](../backup-and-recovery.md) owns the coordinated database/media procedure. Do not maintain another deployment or restore recipe here.

The procedures are **Source-reviewed**. Current execution belongs to [operations verification](verification.md); older successful installation/browser/recovery checks remain **Historically passed** within their original scope. No older-release rollback, arbitrary schema downgrade, zero-downtime upgrade or actual production rollout is established merely by a successful same-release restart.

## Scope and non-negotiable inputs

The delivered deployment form is a complete versioned source checkout with its frozen dependency graph, reviewed SQL/journal, operator scripts and domain/worker/web outputs. The web and worker must use the same approved release. Preserve the previous release separately; do not overwrite a running directory or assume copying the Next standalone output alone creates a recoverable release.

Current compatibility is Node **24.19.0**, pnpm **10.34.6**, PostgreSQL **17** and application schema **17**. The [runtime readiness implementation](../../packages/database/src/readiness.ts) requires the exact schema version; it does not accept an arbitrary newer version. The [migration journal](../../packages/database/migrations/meta/_journal.json) contains seventeen reviewed forward migrations, `0000`–`0016`. There is no root down-migration command or documented automatic schema downgrade.

> **Warning:** A schema-changing upgrade, role-password reprovisioning or recovery can affect every workspace. Before applying it to an existing installation, retain and verify a coordinated database/media recovery set, its matching source/toolchain identity and separately recoverable secrets. A portable workspace archive is not a full-system rollback set. Never delete volumes, edit authoritative ledger rows or change schema metadata to make an incompatible release appear healthy.

Use the [operational checklists](checklists.md) for the concrete change record. Before starting, establish:

| Required input                                                                       | Why it matters                                                                                                                                                  |
| ------------------------------------------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Current and target commit, lockfile/build identity and migration/schema requirements | Distinguishes the intended change from an accidental branch tip or stale artifact. A documentation branch is not automatically an approved production release.  |
| Actual PostgreSQL target and three restricted runtime identities                     | A correct schema on another host does not validate the selected target. Keep connection URLs/credentials private.                                               |
| Complete recovery set and verified cutoff                                            | Database, queue, media and authentication evidence must correspond to one quiesced state; restoring an older cutoff can discard later committed changes.        |
| Recovered configuration/authentication secret and role credentials                   | A source checkout or database dump alone does not recover service secrets or the HTTPS edge.                                                                    |
| Writer/worker inventory, maintenance boundary and service ownership                  | Ingress, all web replicas, worker and external writers must respect the same fence. Read-only browser traffic can still change authentication state.            |
| Workload/capacity, disk/inode headroom, connection headroom and expected downtime    | A small local rehearsal does not demonstrate production-size migration/recovery or the open FA-04 capacity budgets.                                             |
| A tested disposition if any gate fails                                               | Choose before mutation whether failure permits a compatible code switch or requires isolated recovery. Do not invent the plan after losing access to old state. |

Do not infer compatibility from a shared major application version, an apparently additive migration name, a matching schema integer alone or successful startup. Financial calculation definitions, persisted payloads, immutable instrument conventions, media layout and queued work must also remain understandable to the selected release. Review those boundaries explicitly.

## Prepare and rehearse the target release

1. Record the current running release and intended target through the service's approved release record. From an existing checkout, `git status --short --branch` and `git rev-parse HEAD` are read-only source checks; they do not identify what a separate supervisor is actually running. Preserve all local edits.
2. Prepare the target in a new versioned directory using [release preparation](../deployment.md#prepare-a-release). Use the exact pinned runtime/manager and full frozen installation. Build and check that release before maintenance; do not point build/tests at production credentials.
3. Review the target's entire migration suffix and application/queue change. [Migration `0015`](../../packages/database/migrations/0015_financial_source_conventions.sql), for example, replaces broad price constraints with convention-aware guards; [migration `0016`](../../packages/database/migrations/0016_saved_views.sql) adds constrained private preference fields. Forward scripts may alter existing constraints/functions as well as add objects. Their existence does not prove reverse compatibility.
4. Rehearse against a separate restored copy under its matching original release, then apply the intended forward upgrade. Keep source/session/media artifacts private, prevent unintended external actions, and never use a user database as a disposable test target. Record current/target identities and exact results.
5. Compare pinned financial/report DTOs, ledger/cash/quantity evidence, campaign lifecycle and known attachment hashes before and after, accounting for an explicitly reviewed calculation-version change. A changed timestamp, decimal or availability reason is not something to strip merely to make a comparison pass.
6. Rehearse the actual fallback decision. A stop/start of the same build checks restart persistence; switching to a documented compatible older build checks a different boundary. If the only proven fallback is full recovery to the original release/cutoff, state its loss interval and downtime honestly.

An empty-database installation establishes migration availability, not every populated upgrade path. A same-release full-system recovery establishes its stated fidelity, not an older-binary rollback after a newer migration. Consult [verification](verification.md) for which exact scenarios were executed. Unlisted cross-version transitions are **Not run**.

## Handle dependency and toolchain updates as release changes

The [root manifest](../../package.json), [workspace settings](../../pnpm-workspace.yaml), [.npmrc](../../.npmrc) and [lockfile](../../pnpm-lock.yaml) define the reviewed graph. Keep the same graph across web, worker and operator tooling; do not prune build/operator dependencies from this release form. Runtime ranges do not replace the exact release pins.

1. Make a proposed dependency/toolchain update in an isolated development checkout through the repository's normal change review. Record the affected direct/transitive packages, advisory reason and native/contract impact. There is no delivered unattended production dependency updater.
2. Regenerate/change the lockfile only as part of that reviewed source change. In release preparation, `corepack pnpm install --frozen-lockfile` must succeed without rewriting it. Do not use a floating package-manager invocation, `--force`, disabled strict peer checks or an unreviewed override to clear an install failure.
3. Run the declared API drift, formatting, lint, types, unit/UI, isolated PostgreSQL integration, build and release checks in [deployment](../deployment.md#prepare-a-release). Run the relevant browser, native-module, queue/migration and controlled HTTPS/recovery regressions for the change; the [CI workflow](../../.github/workflows/ci.yml) shows the configured checks and test isolation. A configured job is distinct from a passing hosted run.
4. Use `corepack pnpm security:audit` to obtain the then-current advisory result over the locked graph. It requires registry access and is time-dependent; an old zero-advisory report does not establish current security. Preserve TLS/integrity verification and assess an actual advisory rather than hiding it by changing install scope. **Failed:** the fresh Checkpoint 5 audit on 26 October reported seven advisories—two critical, three high and two moderate—in the unchanged graph. The [verification record](verification.md) retains the exact advisory IDs and command result. The current CI advisory gate would fail; no dependency versions were selected or applied by this documentation checkpoint. Resolve that gate through a reviewed lock/source change and repeat the applicable tests, build/artifact and deployment-host checks.
5. Rebuild/release-check on the intended supported platform and smoke-test the deployment host. Native Argon2 must load under that host's OS/CPU/libc. A native override or a copied binary from another host is not a supported compatibility proof.
6. Ship the resulting approved source/lock/toolchain/build as one new release through the upgrade lifecycle. Do not run dependency updates inside a live release or treat a dependency-only change as exempt from backup/compatibility decisions.

Installation and build commands create dependencies/artifacts; advisory checks use the network; integration/browser/recovery tooling creates or modifies isolated test resources. Those are not read-only production diagnostics. [Troubleshooting](../troubleshooting/installation-and-startup.md) owns safe diagnosis of install/runtime errors.

## Fence writes and execute one controlled migration job

Follow the canonical [migration and rollout order](../deployment.md#migration-and-rollout-order), with these upgrade-specific gates:

1. Complete the verified coordinated backup and record its cutoff while ingress and **all** writers/workers are stopped/drained as required by that procedure. Record the exact source financial/metadata context and media manifest. Verify recovery credentials remain available without posting them in the change record.
2. Keep traffic fenced if old and new releases have not been explicitly proven compatible. A rolling deployment is **Not run** unless its actual expand/backfill/contract and mixed-worker behavior were rehearsed; an additive schema change alone does not establish it.
3. Have one deployment controller execute `corepack pnpm db:migrate` from the target versioned repository root with its private operator and runtime bindings. **Modifies state:** this applies application SQL, initializes/upgrades pg-boss and its queues, then provisions runtime-role passwords/grants from their configured URLs. It is not a read-only status or password check.
4. Serialize the whole command across deployment and recovery controllers. The application runner uses advisory lock `1791244800` with a thirty-second lock timeout, but releases it before queue migration and role provisioning. The command is not one global atomic transaction; a later phase failure does not undo every earlier phase.
5. Preserve the complete command's result. Its success message is `Database and queue migrations applied; least-privilege runtime roles provisioned.` A schema-version query, a healthy PostgreSQL container or completion of the application phase alone does not establish that the queue/provisioning phases succeeded.
6. Keep operator credentials out of runtime children. Coordinate the configured runtime credentials with the restarted service environment; reprovisioning passwords while old processes keep using different credentials can leave later connections failing.

Do not auto-migrate in each web/worker replica, run competing migration commands, edit an applied SQL file, use an unreviewed schema-push command or update `app.schema_metadata` manually. The exact-prefix guard compares applied hashes and timestamps/order with the approved journal before accepting existing history. A prefix mismatch needs investigation, not deleted journal rows.

## Verify before admitting traffic

After the complete migration command succeeds, perform the [deployment preflight/start sequence](../deployment.md#migration-and-rollout-order) under the actual intended identities/transport and document each gate separately:

| Gate                              | Verification and limitation                                                                                                                                                                                                                                                                                                                                    |
| --------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Source/artifact integrity         | Approved source/lock/migration identity, fresh build and release-check results. The release checker validates required sources/artifact/dependency closure; it does not by itself prove stale outputs were built from those sources or byte-identical builds.                                                                                                  |
| Database compatibility            | `corepack pnpm db:check` uses the application role for a read-only query, exact schema 17 and PostgreSQL 17. It does not inspect every role or replace migration-history validation.                                                                                                                                                                           |
| Runtime roles, target and storage | `corepack pnpm ops:preflight` checks actual role restrictions, common observed target and verified database TLS. **Temporary filesystem mutation:** its private write/read/hash/delete probe does not establish durable backups or persistence across host loss. Production uses verified TLS; the explicit local plaintext test mode is not a deployment fix. |
| Supervised service startup        | Start web and worker from the same target release using the established supervisor and canonical root commands. The repository supplies no universal systemd/container deployment definition. Stop only owned processes; preserve the documented outer drain window.                                                                                           |
| HTTP/authentication/security      | Public liveness, authenticated web readiness, private worker readiness, actual HTTPS sign-in/out, intended session behavior, same-origin/CSRF denial, unrelated-tenant denial and authorized private media. An anonymous readiness denial is expected authorization, not a healthy authenticated probe.                                                        |
| Financial/source fidelity         | Representative existing cash/quantity/basis/P&L, allocation conservation, account/portfolio scope and pinned report context. Validate complete/partial/unavailable states as well as amounts. Never create a live deposit/trade just to make an otherwise empty health smoke look realistic.                                                                   |
| Worker business state             | Inspect native-snapshot status/revisions for representative workspaces and the safe queue/outbox failure classifications. Worker health-probe success alone is not current business delivery. Snapshots are all-recorded native cash/quantity, not NAV or bulk reports.                                                                                        |
| Recovery and monitoring           | Record the fallback decision, backup cutoff, observed pause/start/error counts, alert ownership and post-change backup plan. Do not certify production RPO/RTO or FA-04 from small-fixture timings.                                                                                                                                                            |

Only admit traffic after the deployment's required gates have actual evidence and the release decision is recorded. If any gate fails, keep the fence and use the decision table below. Retain the previous source and recovery set until the operational retention decision has been satisfied; this guide introduces no automatic deletion policy.

## Choose retry, code reversion or recovery

| Observed state                                                                                                                                        | Safe disposition                                                                                                                                                                         | Evidence needed before proceeding                                                                                                                                                                                                     |
| ----------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Target install/build/release check failed before any shared configuration/database/media change                                                       | Keep the current release serving if its own health is intact; repair/rebuild the target separately. No database rollback is implied.                                                     | Confirm no deployment phase changed shared state, credentials, listener or media. Preserve the failed target's sanitized result.                                                                                                      |
| The same approved release stopped unexpectedly with no data/schema change                                                                             | Diagnose and restart that owned release through the supervisor after the cause is removed.                                                                                               | Readiness and persistence checks prove this restart, not older-release compatibility. Do not run migrations reflexively.                                                                                                              |
| `db:migrate` failed; the failed phase or committed prefix is uncertain                                                                                | Keep traffic/writers fenced, preserve the backup and failed release, inspect safe diagnostics and exact history under operator access.                                                   | Establish the actual target/history and whether application SQL, queue schema or provisioning committed. Do not infer a global rollback.                                                                                              |
| Migration failure is an understood transient connection/lock issue and approved history still matches                                                 | Retry the same reviewed complete migration command after the cause is removed, serialized under the controller.                                                                          | Correct target/release, verified backup, no competing job and recorded previous outcome. Recheck every phase and all postchecks afterward.                                                                                            |
| Applied migration history does not match the approved exact prefix                                                                                    | Stop migration/release attempts and investigate the release/target provenance. Recover the correct approved files if that is the cause; otherwise use reviewed isolated repair/recovery. | Exact error classification, approved journal/files, restricted history inspection and verified recovery set. Never change hashes, delete rows or mark migrations applied to make the guard pass.                                      |
| New application fails after migration; the previous binary's required schema/calculation/payload/queue behavior has been explicitly proven compatible | Remove traffic, drain owned processes, select the retained compatible release and run its complete postchecks before restoring traffic.                                                  | A recorded compatibility rehearsal on the now-applied state. The shared schema integer alone is insufficient. Do not run a lower release's migrator against unknown newer history.                                                    |
| The previous release requires another schema or cannot interpret new persisted/queued data                                                            | Do not start it against the upgraded database. Prefer a reviewed forward fix, or decide coordinated recovery to the matching prior release/cutoff.                                       | Matching source/lock/runtime, database/media/secrets recovery set, rehearsed isolated restore, explicit loss interval and controlled cutover. A prior schema-9 runtime is not assumed to accept schema 17.                            |
| Data/media integrity or an incomplete release requires recovery                                                                                       | Preserve the failed system, keep a write fence and restore a matching coordinated set into an empty isolated target using [backup/recovery](../backup-and-recovery.md).                  | Fidelity, runtime security/auth/media/queue validation, recovery cutoff and a single-writer cutover decision. An older recovery point may lose later writes; never restore media alone or overwrite an existing target as a shortcut. |

There is no safe generic “undo the last SQL migration” step in this release. Forward SQL includes immutable source/provenance, guarded functions/constraints and new persisted capabilities. Removing its objects does not undo financial activity or necessarily make older code understand the surviving data. An operation that merely reduces the schema metadata integer conceals the incompatibility.

## Handle failure and collect the change record

Use [database/migration troubleshooting](../troubleshooting/database-and-migrations.md) for exact-prefix, role, schema and lock failures. CLI tools intentionally report sanitized operation/code summaries; do not enable credential-bearing exception or SQL logging just to obtain a longer message. Keep a bounded evidence window with:

- Current/target/recovery commit, build/lock/migration identity, PostgreSQL/schema/tool versions and UTC change/cutoff times.
- Which complete command/phase succeeded or failed, its exit status and safe classification; whether any application, queue or runtime-role change is known to have committed.
- Whether traffic was fenced, which owned service instances drained/restarted, and whether another controller was active.
- Preflight/readiness/security/financial/media/snapshot results and their source/revision scope; distinguish expected denial/unavailability from failure.
- The verified recovery set's protected manifest reference, chosen disposition, potential lost-write interval and actual cutover result.

Do not include passwords, database URLs, `.env`, cookies, CSRF tokens, dumps, complete release reports, source statements, journal text or raw queue/financial payloads in a shared incident ticket. Use [sanitized diagnostics](../troubleshooting/diagnostics.md) and [security operations](security-operations.md) for restricted evidence and credential/session response. Recovery can resurrect pre-cutoff sessions/memberships and pending jobs; inspect them under the recovery procedure rather than truncating queues or bypassing authorization.
