# Routine maintenance

Reviewed **26 October 2026** for Phase 19 Checkpoint 5 against committed Checkpoint 4 `b75b04cc92dbe89bb4bf131600fd1cb0a31a77e4`; unchanged application baseline `5132900a03efabaeb307787531546987228220e7`. This document owns recommended operating cadences and maintenance records. [Operations](../operations.md) owns runtime/health/logging/capacity behavior; [deployment](../deployment.md), [backup and recovery](../backup-and-recovery.md), [configuration](../getting-started/configuration.md) and [security](../security.md) own their detailed procedures.

The schedule below is a **recommendation**, not installed automation or an operational guarantee. Select a named operator, substitute, private evidence location and actual escalation destination before relying on it. The repository supplies no cron service, monitoring vendor, backup scheduler, external alert recipient, general retention job or automatic dependency updater. Application queue supervision/native projection processing is implemented; it is not a general maintenance scheduler. The [verification record](verification.md) distinguishes fresh disposable checks from target procedures that remain unexecuted.

## Prerequisites and operating boundaries

- Use the approved release and its complete locked dependencies, Node 24.19.0/pnpm 10.34.6 and PostgreSQL 17/schema 17. [Environment inventory](../environment-inventory.md) distinguishes declared ranges from verified environments.
- Keep application, authentication, queue and one-shot operator identities separate. Inspect the smallest authorized scope; a maintenance operator is not permission to bypass tenant authorization or disclose private source documents.
- Maintain durable private media and coordinated database/media backups. Do not interpret a portable workspace archive as recovery of global identities, sessions, database privileges, host secrets or every workspace.
- Check affected scope and retain a usable coordinated backup before potentially destructive maintenance, credential/permission repair or recovery. Preserve the original system and recovery sets when investigating corruption. Do not repair a report by editing authoritative ledger/source/allocation/audit data.
- Record the source revision and report context when inspecting financial discrepancies. Native worker projection status, account NAV, campaign P&L and independent broker reconciliation answer different questions.
- Separate operational log expiry from durable source/audit retention. No routine below authorizes pruning application facts, migration history, import provenance, original plans, strategy versions or outbox records.

The procedures in this document are **Source-reviewed** against the linked implementation. Actual completion must be recorded for the selected deployment; a checklist tick without evidence is not verification.

## Daily or before each active session

For a continuously running service, use at least a daily human review in addition to deployment-selected automated probes. For an intermittently run local journal, perform these checks before recording/importing activity and after the last save. Frequency must fit the deployment's agreed availability and recovery needs.

| Check                       | Safe action                                                                                                                                                                                                 | Expected evidence and response                                                                                                                                                                 |
| --------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Correct release and context | Confirm supervisor release identity, selected workspace and paper/live environment. Compare web/worker release identities.                                                                                  | One reviewed release; no accidental test/production crossover. Stop a rollout if releases or schema are incompatible.                                                                          |
| Web availability            | Check public liveness and authenticated readiness through the real intended origin. Distinguish `401`/`403` from `503`; keep session credentials private.                                                   | Correct uncached health response; schema 17/PostgreSQL 17/auth query ready. Liveness alone proves neither database nor storage. See [health checks](../operations.md#health-checks).           |
| Worker/queue                | Check private worker readiness and recent heartbeat events; inspect durable native-snapshot latest/processed revisions and failure classification for the relevant workspace.                               | Queue round trip works and native delivery status is understood. A green probe does not prove the financial projection is current or establish NAV. See [outbox](../financial-outbox.md).      |
| Database and capacity       | Inspect restricted aggregate connection/pool statistics, repeated database failure events and disk/inode headroom. Compare with agreed thresholds and release overlap budget.                               | No sustained pool waiting/exhaustion, unexpected restart or disk-pressure trend. Escalate before writes fail; do not remove safeguards to conceal load.                                        |
| Media                       | Check storage mount/ownership and capacity; retrieve a known authorized non-sensitive attachment through the application.                                                                                   | Ready metadata resolves to its intended private bytes, with no public exposure. A successful download of one object is a sample, not full archive integrity proof.                             |
| Backup freshness            | Check the last completed coordinated recovery-set time, verified off-host copy and failure notification. Preserve the previous known-good set if a new run failed.                                          | Backup age within the approved policy, recoverable encryption keys and a clear cutoff. Follow [backup and recovery](../backup-and-recovery.md) for actual capture/validation.                  |
| Logs and security           | Review safe failure/status codes, request IDs, sign-in denials and unexpected role/session activity. Check that collection includes stdout and stderr.                                                      | No unexplained sustained failures; redacted evidence retained privately. A classifier-only error requires diagnosis, not enabling sensitive body/SQL logging.                                  |
| Financial workflow          | After recording/importing, inspect persisted result/duplicate decisions and save state before retrying or signing out. Use independent statement comparison where a reviewed source statement is available. | The actual operation outcome is known; no duplicate source/cash recreation. Journaling save, financial commit and statement acceptance remain distinct. See [manual](../user-guide/README.md). |

If a health or financial check fails, record its time/scope and use the matching [troubleshooting category](../troubleshooting/README.md). Preserve logs and affected data. A browser response interrupted after a write is not proof of rollback; inspect the persisted record first; use an original retained idempotent retry only where that workflow provides one.

## Weekly

1. Review backup job results and recovery-set completeness, including database, private media, release identity and separately recoverable secrets/keys. Check off-host verification and expiry decisions against the approved policy. Schedule a safe restore rehearsal when evidence is stale or the release/storage topology changed.
2. Review log collection, disk growth and retained log access. Confirm that the deployment's rotation handles both streams without creating an unbounded local spool. The application does not install a log-rotation configuration or choose its filesystem path.
3. Review capacity trends against representative history: financial record growth, media bytes/inodes, database size, active/waiting connections, request failures/latency and worker delivery lag. Use bounded aggregates and approved monitoring permissions, not copied financial payloads. Keep [FA-04](../final-audit.md) and [measured performance limits](../performance.md) visible.
4. Review dependency advisories against the committed lockfile using the command below. Triage the advisory and affected path; do not automatically install floating versions or modify a running release. Follow the reviewed build/test/release process for a fix.
5. Review service/session access and operator membership with the authorized owner/security process. Check expiring TLS certificates, database trust material and monitoring-session validity. A known session lasts seven days without sliding; do not create a noisy repeated-login monitor that triggers persisted throttling.
6. Compare the actual deployment configuration names, release pins, storage path/permissions and runtime identity boundaries with the current [configuration](../getting-started/configuration.md) and [deployment](../deployment.md) documents. Record drift privately without printing credentials.

Weekly does not imply that a security incident, expiring certificate or failed backup may wait until the next review. Existing incident severity and approved policy determine urgency.

## Monthly and after significant changes

1. Rehearse coordinated recovery in a newly isolated target using the reviewed procedure and synthetic or privately controlled data. Verify financial/source/audit fidelity, role/RLS boundaries, private media bytes, session policy and current outbox/worker behavior before considering cutover. The repository drill supports a disposable local test fixture; it does not prove an arbitrary production snapshot or offsite system is recoverable.
2. Review measured recovery duration, possible data-loss interval and restore-test age against the deployment's accepted objectives. ADR 0008 proposes daily backups, 30-day retention, RPO at most 24 hours and RTO at most four hours; these are policy proposals, not achieved production guarantees. Keep the operational backup procedure authoritative.
3. Review workload growth and alert thresholds with representative concurrency. A small functional smoke run does not certify million-fill reporting, ten active readers, memory-leak behavior or asynchronous bulk work. The worker still does not implement generic large-report/import processing or failed-business-job redrive.
4. Review dependencies, runtime/OS/PostgreSQL patches, pinned image digest and supply-chain changes as a planned release. Preserve compatibility and native Argon2 verification. Changing the lockfile, runtime or image requires fresh relevant tests, release verification and rollback/schema review; it is not an in-place production housekeeping command.
5. Review secrets/key access, recovery custody and incident-driven revocations. Rotate using the deployment's protected secret system and documented restart/cutover plan; test new database credentials and certificate trust before removing prior access. Authentication-secret changes can invalidate existing sessions, and restored sessions/memberships need explicit security review. Do not publish values or weaken TLS to make rotation pass.
6. Review documentation, operator ownership and real escalation/alert delivery. Test a safely controlled failure on a disposable or approved rehearsal target so the actual notification path is observed. There is no repository-defined support mailbox or incident service to assume.

Repeat relevant checks after release/schema changes, a database restore, storage movement, secret/certificate rotation, supervisor/proxy changes or an incident. Follow [deployment](../deployment.md) for release ordering and compatibility gates; never edit an applied migration or choose an older database as an ordinary code rollback.

## Available checks and command boundaries

Commands below run from the reviewed source release's **repository root** on the documented Linux/POSIX environment, with the pinned toolchain and frozen dependencies. They are independent checks, not a maintenance script to run unattended. Their existence is **Source-reviewed**; the [verification record](verification.md) identifies executions performed for this checkpoint. No unlisted current production check is implied to have passed.

| Command                        | Source, prerequisites and effect                                                                                                                                                                                  | Expected result and limitation                                                                                                                                              |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `corepack pnpm db:check`       | [Root script](../../package.json), [database checker](../../scripts/database-check.ts). Requires private runtime application URL; opens read-only compatibility queries, no DDL or source mutation.               | Exit 0 for supported PostgreSQL/schema. Does not establish auth/queue/media readiness, full migration-history integrity or TLS verification by itself.                      |
| `corepack pnpm security:audit` | [Root script](../../package.json), [CI](../../.github/workflows/ci.yml). Requires registry access or its configured response path; sends dependency metadata and may update tool caches, not application records. | Executes `pnpm audit --audit-level=low`. Advisory results are time-dependent; network failure is not a clean audit. Review and remediate through a separate tested release. |
| `corepack pnpm release:check`  | [Release verifier](../../scripts/release-check.ts). Requires complete locked source/dependency/build outputs and exact pinned runtime/package manager/native hashing. Does not deploy or migrate.                 | Exit 0 with release evidence; does not certify target TLS/storage, public deployment, backup durability or FA-04 capacity.                                                  |

CI is configured to run dependency audit, frozen install, isolated configuration/database migration checks, aggregate verification/build, release verification, controlled HTTPS smoke, isolated recovery and browser tests. [The workflow](../../.github/workflows/ci.yml) is configuration evidence; inspect its actual run result for the exact commit before promotion. A local pass is not an executed hosted CI run. The seven-day retention of failed-browser artifacts in CI is separate from proposed operational-log and backup retention.

For health probes, aggregate SQL and sanitized logs, use [operations](../operations.md) and [diagnostics](../troubleshooting/diagnostics.md). Do not copy raw connection strings into commands, save browser cookies in shared scripts or enable full-statement/parameter logging during routine checks.

## Storage, database and retention work

**Supported invariant:** ready media, lifecycle metadata and coordinated backups must remain consistent. Pending, removed, staged or apparently orphaned files are not permission for an operator to run recursive deletion. The repository has no general scheduled orphan-media janitor or user-facing bulk purge. Investigate lifecycle state using the supported application/diagnostic path, preserve a recovery set and escalate unresolved inconsistencies. Never remove a volume to fix a startup, migration or capacity problem.

**Recommended policy:** approve separate capacity/retention plans for operational logs, private backup sets and durable financial/source/audit data. ADR 0008's initial 14-day operational-log and 30-day backup proposals do not authorize deleting immutable application history. An expired backup should be removed only after the approved retention policy confirms newer independently verified/restorable sets and recoverable keys. The operator's backup system, not this application, must implement/test expiry and offsite controls.

**Database maintenance:** monitor PostgreSQL capacity and the deployment's ordinary statistics/autovacuum health with a qualified database operator. No routine application task is supplied to rebuild indexes, vacuum all tables, purge `auth.rate_limit`, discard audit/import provenance or truncate `queue.job`. Any separately proposed database maintenance must have reviewed scope/locking/capacity, a usable backup, a maintenance window where required and a verification/rollback plan. Keep runtime identities narrow; operator privileges are not a reason to run write SQL against authoritative data.

**Queue retention is different:** pg-boss queue-row expiry/retention settings are implemented in the [queue migration](../../apps/worker/src/migrate.ts) and runtime supervision is enabled. Those settings are not a policy for deleting financial outbox facts, projection checkpoints or financial commands. Do not manually mark jobs complete/delivered to make monitoring green. Use the authenticated status and authorized recovery process documented in [financial outbox](../financial-outbox.md).

**Potentially destructive action:** deleting/expiring a backup, changing ownership recursively, rotating/retiring credentials, altering database privileges, restoring data or replacing a storage mount requires the deployment's coordinated backup and reviewed target plan first. Retain prior recoverable state until verification and cutover are complete. This guide does not supply a generic delete/cleanup command because no single target/path/policy is safe to assume.

## Record the maintenance outcome

Use a private operator record with the following fields; do not put real credentials or private financial payloads into a public repository issue:

| Field              | Record                                                                                                                                          |
| ------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------- |
| Identity and scope | Operator, reviewer where required, deployment/release commit, schema, affected services/workspaces using redacted identifiers.                  |
| Timing and trigger | Timezone-qualified start/end, cadence or incident/change trigger, planned impact window and actual user impact.                                 |
| Prechecks          | Health/context, capacity, exact recovery-set identity/cutoff and verified copy/key availability where the action can be destructive.            |
| Action             | Exact reviewed procedure/command and target, read-only versus state-changing classification, private configuration source names without values. |
| Verification       | Exit/status, sanitized request/event codes, report generation/definition, service/media/backup checks and whether alert delivery was observed.  |
| Exceptions         | Failed or unexecuted checks, unresolved discrepancies, preserved rollback/recovery state, owner and next review time.                           |

Close a task only when its specific verification succeeds. If service health recovers but media, backup freshness, financial reconciliation or projection generation remains wrong, retain the unresolved issue. Use [troubleshooting](../troubleshooting/README.md), preserve evidence and escalate through the deployment's established private channel.
