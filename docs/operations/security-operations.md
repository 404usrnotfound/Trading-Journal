## Required controls and a review schedule

The controls in the next table are implementation/deployment requirements, not optional ways to hide a failed check. The suggested cadence is a starting policy for the organization operating the installation. No scheduled access review, certificate renewal, secret rotation, advisory alert or backup-retention service is installed by the repository.

| Review                   | Required invariant / evidence                                                                                                                                        | Suggested cadence to adopt locally                                                                  |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------- |
| Access                   | Only intended provisioned identities and current workspace roles can read/change authorized records; operator/host access is separately restricted.                  | On join/change/leave and incident; monthly membership/operator-access review.                       |
| Sessions and credentials | Seven-day non-sliding sessions, fresh authentication for security APIs, same-origin/CSRF protections, distinct database identities, secrets kept out of logs/builds. | On suspicious access, password/secret changes and recovery; monthly review of the operator process. |
| Dependencies and release | Frozen lockfile, reviewed dependency changes, advisory check and required regression/release gates.                                                                  | Every release/dependency change; a weekly advisory review is a proposed operational cadence.        |
| Database privileges      | Runtime roles remain restricted and separate, with no role membership/ownership escalation; intended TLS transport.                                                  | After provisioning, migration, restore or credential change; before admitting a release.            |
| Media, edge and logs     | Private media ownership/modes, trusted HTTPS, private worker/database listeners, private response handling and sanitized operational evidence.                       | After infrastructure changes; regular host/certificate/capacity checks under the site's policy.     |
| Recovery material        | A coordinated complete recovery set, separately protected secret/key recovery, and demonstrated isolated restoration.                                                | At the adopted backup schedule and after relevant changes; rehearse at a policy-defined interval.   |

Record the actual responsible operator, reviewed release, date/time with timezone, scope, result and unresolved exceptions in the site's restricted change/incident record. The repository supplies neither an approved-recipient directory nor a response SLA. [FA-04](../final-audit.md) remains open; a security review or dependency scan does not certify production reporting capacity.

## Review accounts, memberships and sessions

1. Use the intended canonical origin and a valid authorized identity. Confirm the release and workspace before interpreting access. A sign-in identity and a workspace membership are separate facts; do not create a replacement owner to recover missing membership.
2. Review workspace owners/editors/viewers against the organization's approved roster through its authorized administration process. There is no delivered invitation or membership/role editor page and no documented general member-management API. Establish a separately reviewed administrative process if membership changes are required; SQL setup in a test fixture is not an ordinary support procedure.
3. Verify representative allowed reads/writes and expected denied access using approved test identities/data in isolation. UI visibility alone is not a permission check. Tenant requests recheck current membership inside an actor/workspace-scoped transaction and preserve RLS; do not disable RLS or grant a broader runtime role to repair access.
4. Inspect the affected user's sessions through an authorized integration only when needed. The public gateway supports `GET /api/auth/sessions` and `POST /api/auth/revoke-session`; both require a session created less than five minutes earlier, and revocation additionally requires the current session's same-origin CSRF proof. It returns safe session IDs/times, not bearer tokens, and only revokes a session owned by that user. There is no browser session-manager screen or delivered operator endpoint to enumerate/revoke every user's sessions.
5. For a normal departure or incident, revoke the relevant access using the established authorized process, then verify a new server request is denied. Already loaded browser bytes/drafts may remain visible until refresh; logout does not erase information already downloaded.

The narrow [auth gateway](../../packages/server/src/auth-gateway.ts) exposes session read/list and the reviewed sign-in, sign-out, password-change and single-session revocation actions. Unsupported library signup/reset/social/profile endpoints remain unavailable. [Server authorization](../../packages/server/src/services.ts), [authentication configuration](../../packages/server/src/auth.ts) and the [authentication ADR](../decisions/0003-authentication-and-tenancy.md) define the actual boundaries. No MFA, mail verification or invitation system is delivered.

## Change a password or recover a compromised user

Choose the path that matches the available evidence and authority; these are credential/session changes, not financial recovery operations.

| Supported path                              | Preconditions and effect                                                                                                                                                                                                                                                                                   | Verification                                                                                                                                                                    |
| ------------------------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Normal **Sign out**                         | Current session and mutation proof; does not require the five-minute freshness check. Revokes that session.                                                                                                                                                                                                | A server read using that old session no longer authorizes access.                                                                                                               |
| Authorized `POST /api/auth/revoke-session`  | Fresh own session, same-origin CSRF proof and an owned safe session ID. Revokes the selected session; selecting the current one signs it out.                                                                                                                                                              | The selected old session fails; unrelated authorized sessions behave according to their actual state.                                                                           |
| Authorized `POST /api/auth/change-password` | Fresh session, current password, accepted new password and mutation proof. Gateway forces revocation of other sessions; current reviewed behavior replaces the cookie and invalidates all previous sessions. No browser password editor is delivered.                                                      | New password/sign-in and replacement cookie work; all prior cookies fail. The [gateway integration test](../../tests/integration/auth.test.ts) checks those exact distinctions. |
| Operator password recovery                  | Confirm identity and installation through a private authorized process, then use the supported one-shot `user:create --reset-password` procedure linked below. Changes that existing user's password and revokes every prior session. It does not create a nonexistent identity or repair workspace roles. | Successful tool outcome, new sign-in to existing authorized records, and old-session rejection.                                                                                 |

For forgotten/compromised credentials when a fresh authenticated password change is unavailable, follow the exact [operator recovery command and safeguards](../troubleshooting/authentication-and-security.md#forgotten-password-requires-an-operator-recovery). From the repository root, that existing `user:create` script accepts a hidden trusted-TTY password or a secure one-shot `BOOTSTRAP_PASSWORD` environment binding. New passwords require 12–128 characters. Never put a live password in shell arguments/history or replace auth password hashes with SQL. The bootstrap/recovery tool removes its consumed binding from its process environment, but this is not permission to publish the parent environment or recorded terminal output.

The [recovery implementation](../../packages/server/src/services.ts) requests and consumes the supported Better Auth reset token inside the operator process, revokes sessions and attempts an `auth.operator-password-reset` audit record. A reset token is not emailed or exposed as a public recovery API. Existing-account bootstrap deliberately preserves credentials; running ordinary bootstrap again is not password rotation. Password change/recovery writes Argon2id through the reviewed [credential hooks](../../packages/server/src/credentials.ts); recognized old scaffold hashes remain verifiable until a supported password update replaces them.

These operations are **state-changing** and can interrupt the affected user. Preserve relevant incident evidence and coordinate the target identity before changing it. A password problem alone does not justify a destructive database restore. For broad auth-database/host compromise, a one-user reset is insufficient: continue with the scope-specific containment plan below and the organization's reviewed operator response.

## Plan secret and database credential rotation

No dedicated secret-rotation command, key ring, automated secret-version distribution or graceful dual-key transition is delivered. The following is a **Source-reviewed operator plan**, **Not run as a production rotation procedure**. Adopt and rehearse the host/secret-manager details before a live change.

### Rotate runtime database credentials deliberately

1. Establish which credential was exposed: application, authentication, queue or operator. Confirm target host/database, exact deployed release, reviewed migration state and current grants. Preserve a verified coordinated recovery set and separately recoverable secrets before migration/provisioning or any recovery action that could remove/overwrite data. Preserve incident evidence without retaining exposed values in a public report.
2. Schedule a maintenance/write fence and drain the affected web/worker processes using the deployment's actual supervisor. Existing PostgreSQL sessions may remain usable after a password change; a secret update alone does not terminate a compromised connection. Have the authorized database operator assess known sessions and containment without indiscriminately terminating another system's workload.
3. Generate independent strong credentials through the site's secret mechanism and update the intended fixed-role bindings. `DATABASE_URL`, `AUTH_DATABASE_URL` and `JOB_DATABASE_URL` identify `journal_app`, `journal_auth` and `journal_jobs`. Keep URL userinfo private and correctly encoded. Do not substitute the administrator/migration connection as a runtime fallback.
4. Use the reviewed operator provisioning/release path, not ad hoc ledger edits. The existing `db:migrate` script applies application and queue migrations **and** provisions all three runtime passwords from those URLs, plus reviewed queue grants. It does not replace inspection of existing memberships/ownership/privileges, and is not a harmless standalone one-role rotation command; inspect pending migration effects and the [migration procedure](../troubleshooting/database-and-migrations.md) before executing it. There is no separate `rotate-password` script. The [provisioner](../../packages/database/src/migrate.ts) requires passwords of at least 24 characters, parameter-safe PostgreSQL quoting and SCRAM password encryption; it deliberately suppresses raw failed statements containing values.
5. Update secret bindings consistently for every affected replica/process, restart with fresh pools, and verify role-specific connections, schema/readiness, queue health and least privilege under the [deployment checks](../deployment.md). The web configuration still requires its declared queue URL even though web does not open a queue pool. Rotating the jobs credential therefore requires reviewing both web configuration and worker runtime bindings.
6. Through authorized tooling, verify new connections work and the exposed credential no longer opens a new connection. This does not prove that all old connections or copied data were removed. Review connection containment, affected hosts and possible unauthorized writes separately before lifting the write fence. Protect updated recovery bindings and record the completed version transition without their values.

Editing `.env` does not alter PostgreSQL role passwords, and `env:init` preserves an existing file rather than rotating it. Changing `POSTGRES_PASSWORD` does not rewrite a pre-existing initialized Docker volume. Never delete that volume to make the credentials agree. Process environment values take precedence over `.env`; configuration/pools are cached and require affected process restarts. [Configuration](../getting-started/configuration.md) owns the complete precedence and consumer inventory.

### Rotate authentication signing material with session consequences

`BETTER_AUTH_SECRET` is one server-only value used by Better Auth and the application's session-bound CSRF HMAC and login-identity HMAC. Keep the same intended value across web replicas and ordinary restarts, and preserve it separately for legitimate recovery. The parser enforces at least 32 nonblank characters; this is not proof of entropy. Local initialization generates random secret material, but no external secret store is provisioned.

For confirmed exposure, plan a coordinated change on all web replicas under the maintenance boundary, then restart them. A changed secret can invalidate signed cookie/authentication material and changes the CSRF derivation and login-counter identity keys; it is not equivalent to database session revocation or a user's password reset. No delivered key-rotation test, dual-secret grace period or atomic all-user session-revocation workflow is established. Define/rehearse the intended global session outcome through an authorized operator plan rather than claiming that changing this one value erases stored sessions, prior leaked data or all attacker access.

Verify fresh normal sign-in, session reads, same-origin mutation proof and protected readiness using approved synthetic activity. Check the intended handling of old sessions explicitly, while retaining rejection of wrong-origin/missing-proof requests. During recovery, an old database/auth secret can restore pre-cutoff sessions or memberships; complete the required revocation/access review before reopening ingress. Do not silently roll back to a compromised secret to recover login availability.

### Protect operator, storage, TLS and recovery secrets

Operator/database-administrator credentials and `MIGRATION_DATABASE_URL` belong only to short-lived authorized setup/migration/recovery processes. Runtime launchers filter them out of web/worker children; do not defeat that boundary. Restrict the host accounts and secret-store access able to invoke these tools. Provisioning authority is a trusted administration boundary, not an end-user role.

Certificate keys, private CA trust, secret-manager access and backup encryption keys are deployment responsibilities with no application-managed rotation service. Keep recovered keys/credentials separate from ordinary public artifacts. A password-free roles dump still requires runtime credentials from protected recovery bindings; a database dump is not a complete secret backup. Before removing an old encryption key, verify every retained recovery set that depends on it remains decryptable through the approved recovery channel. Never destroy the only recoverable key merely to meet a rotation date.

## Maintain least privilege, private storage and HTTPS

- **Database:** `journal_app`, `journal_auth` and `journal_jobs` are distinct non-owner runtime identities. They must remain `NOINHERIT`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOBYPASSRLS`, `NOREPLICATION`, without membership in any other role or ownership/escalation paths. `NOINHERIT` alone does not prevent `SET ROLE`. The non-login reviewed migration owner has different trusted capabilities and must not become a runtime login. Restore reviewed owners, ACLs/default grants, forced RLS, triggers and function search paths rather than granting broad privileges to clear an error. The [production preflight](../../scripts/operations/production-preflight.ts) checks representative privileges/transport and rejects unsafe role facts; readiness alone does not establish them. It also probes private storage, so it is not wholly read-only.
- **Media:** keep `STORAGE_ROOT` outside public/build roots, with intended operator-controlled ancestry, private directories `0700` and objects `0600`. [Local storage](../../packages/server/src/storage.ts) rejects symlinks/unsafe modes and uses immutable exclusive writes; it does not defend against every privileged same-UID host compromise. Do not chmod recursively to world-readable, publicly mount restored attachments, remove provenance or delete pending objects as a routine repair. Attachment envelopes/dimensions and byte limits are not antivirus, full decoding or PDF content safety. Downloads remain untrusted in external tools.
- **Transport:** production requires the canonical HTTPS `APP_ORIGIN`, trusted edge TLS, no caching/transformation of private nonce-bearing HTML/RSC/API/media, and preserved CSP/no-referrer/nosniff/frame denial. HSTS does not provision a certificate. Keep web/worker/database listeners private as specified in [deployment](../deployment.md). Remote PostgreSQL transport requires certificate-verified `sslmode=verify-full` under preflight; the local plaintext allowance is an isolated loopback check option, not permission to disable production TLS verification.
- **Browser and identity boundary:** preserve exact Origin and session-bound CSRF validation, host-only HttpOnly/Secure production cookies and fresh per-document nonce generation. Do not add wildcard origins, disable CSP, expose reset/signup endpoints, trust arbitrary forwarding headers as identity or remove login admission limits. The per-identity persisted limit and bounded credential work in [FA-03 remediation](../audit-remediation.md) are availability/security controls, not a production capacity certification.

## Respond to suspected exposure

1. Establish incident scope/time and a responsible authorized operator. Preserve restricted logs, release identity, audit/source revisions and relevant recovery sets before changing evidence. For active compromise, use the site's reviewed ingress/host containment and write-fence mechanism; the application has no emergency lockdown toggle. Avoid publishing an exposed credential in the incident ticket.
2. Classify the exposed capability: one user password/session, authentication signing secret, one runtime DB credential, operator credential, private media, backup/decryption key or host. A one-user reset does not contain operator/host compromise; changing signing material does not correct unauthorized financial events.
3. Follow the matching supported credential/session action or reviewed rotation plan. Preserve security controls. If privileged data integrity is uncertain, prevent further writes and escalate for recovery/invariant review; do not edit ledger, import, outbox, session or audit rows as an improvised cleanup.
4. Review possible financial/source, membership and media exposure at the relevant revisions. Auth security events record reviewed successful actions, but audit insertion is best effort after the library commits; `auth.audit-write-failed` means the auth result may have succeeded without that audit row. Absence of an event is not proof of no access or no completed command. Source: `createAuthAuditor` in [gateway](../../packages/server/src/auth-gateway.ts).
5. Before restoring/overwriting anything, retain a verified coordinated backup and preserve the original target. Rehearse in a new isolated target through [backup/recovery](../backup-and-recovery.md), accounting for resurrected sessions/memberships and pending jobs. Restoration is not evidence that compromised credentials are safe or that no data was exfiltrated.
6. Verify expected allowed access, rejected prior compromised access, least privilege, current service readiness, representative private-file access, financial invariants and durable backup continuity. Record precisely which checks passed and what remains unverified before the responsible operator releases the actual containment boundary.

## Keep operational evidence private

Application/worker structured logs use stdout; failures may also use stderr and framework/tool output. The [logger](../../packages/server/src/logging.ts) allowlists fields, redacts credential/body paths and serializes error classifications instead of raw stacks/messages. It is not a general sanitizer for free-text messages, PostgreSQL/edge output, screenshots, HAR, Playwright traces or a support archive. Safe IDs can still identify a user/workspace/job and need restricted handling.

Collect the smallest reviewed record: commit, time/offset, route/action, status/code/request ID, affected role/component and safe verification outcome. Follow the [sanitized report template](../troubleshooting/diagnostics.md#collect-a-sanitized-diagnostic-report). Exclude `.env`, environment dumps, cookies/CSRF/Authorization, connection URLs/passwords, reset tokens, hashes/raw auth rows, private notes/media, source files and backups. Do not enable full SQL/parameter logging to diagnose role-password provisioning; the statements can contain secrets even when the application's failure message is sanitized.

The application does not install log shipping/rotation, an auth-audit browser, central SIEM, automatic notifications, malware scanning or an evidence-retention scheduler. Define those responsibilities and access/expiry rules with the deployment owner. Operational log expiry must not erase authoritative financial/security provenance to satisfy a disk-space target. Source evidence and historical test results support the controls above; live host compromise response, certificate/secret rotation, external log storage and organization-specific review procedures remain deployment-specific and unverified until rehearsed there.
