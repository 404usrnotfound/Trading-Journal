# Plan, verify and recover a backup

Reviewed **26 October 2026**, Phase 19 Checkpoint 5, against committed Checkpoint 4 `b75b04cc92dbe89bb4bf131600fd1cb0a31a77e4` and application baseline `5132900a03efabaeb307787531546987228220e7`. This guide is **Source-reviewed**. [Checkpoint verification](verification.md) records newly executed disposable checks; dated earlier [operator recovery evidence](../backup-and-recovery.md#verified-evidence-and-remaining-gates) remains **Historically passed**. No production backup service, offsite store, recovery objective or cutover is established by writing this guide.

Use this guide to choose the right recovery set, apply completion gates and decide when restoration is safe. The existing [complete SQL/media procedure](../backup-and-recovery.md) owns the executable database/global-role/media recipe. The [user manual](../user-guide/imports-and-exports.md) owns the delivered portable-workspace UI. This document links those procedures rather than maintaining a second dump/restore sequence.

## Select the protection boundary

| Need                                                              | Supported mechanism                                                                                                                                                              | What it does not recover                                                                                                                                                            |
| ----------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| A bounded workspace copy, portability or a same-version rehearsal | Owner **Data & backups** → complete workspace backup, then restore into a new verified workspace                                                                                 | Authentication credentials/sessions, old memberships, private member views, global roles, host/deployment configuration and secrets; no merge/overwrite into an existing workspace. |
| Complete application recovery after host/database/media loss      | Coordinated PostgreSQL dump, global roles, private media, exact release and separately protected configuration/secrets using the [operator procedure](../backup-and-recovery.md) | A database dump alone omits global roles and filesystem bytes. SQL/media archives omit the secret-recovery system and external deployment resources.                                |
| An analysis extract or evidence subset                            | Supported filtered JSON/CSV export                                                                                                                                               | It is not a restorable workspace archive or an operational recovery set.                                                                                                            |
| A tighter-than-last-logical-backup recovery point                 | A separately selected physical-backup/WAL/PITR design coordinated with media versions                                                                                            | No WAL archive/PITR service, media rewind, HA failover or automated failover control is delivered/configured by this repository.                                                    |

Portable archives require the exact schema/calculation manifest and retain their [record/media/byte bounds](../user-guide/imports-and-exports.md#download-a-complete-owner-workspace-backup). The current application schema is **17** according to [readiness](../../packages/database/src/readiness.ts) and the [reviewed migration journal](../../packages/database/migrations/meta/_journal.json); the schema in an older recovery set must be interpreted with its matching release. The `journal-workspace/1` label is not a cross-version migration promise.

The implemented private store is local POSIX storage on a persistent private path. An S3/shared-object-store alternative appears in architecture/ADR design but has no delivered adapter. Do not select an unimplemented storage provider or assume that copying one host's directory protects independent hosts. Source: [private storage](../../packages/server/src/storage.ts), [feature inventory](../feature-inventory.md), [environment inventory](../environment-inventory.md), [architecture](../architecture.md) and [ADR 0007](../decisions/0007-private-storage-and-durable-jobs.md).

## Required controls and proposed operating policy

| Control                                                    | Requirement or status                                                                                                                                                                                                                                                           |
| ---------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Complete recovery set and coherent cutoff                  | **Required for the supported logical recovery procedure.** Preserve the full database, approved global roles, media, exact release and separate secret/configuration recovery. Stop all writers while coordinating database/files.                                              |
| Empty target and preserved original                        | **Required.** Restoration and cutover change persistent state. Preserve current data/recovery evidence before potentially destructive replacement; restore into a new empty isolated target. No reset or volume deletion is a first-line fix.                                   |
| Confidentiality and authenticity                           | **Required before off-host transfer/use.** Protect private artifacts, encrypt transferred archives, authenticate the manifest, verify hashes and retain recoverable keys separately. The deployment must select/provision these systems; the repository has not installed them. |
| Least-privilege runtime roles and authorized backup access | **Required.** Do not give a runtime role backup-superuser/BYPASSRLS capability. Use a separately reviewed operator backup/restore identity and preserve runtime isolation after restore.                                                                                        |
| Backup/restore completion verification                     | **Required before claiming recovery.** All command exits, expected sizes/hashes, roles/security, financial results and ready media must pass; a written archive or healthy process alone is insufficient.                                                                       |
| Daily backup, 30-day retention                             | **Proposed policy**, from [ADR 0008](../decisions/0008-testing-and-operations.md). Select a deployment schedule/retention after measuring capacity, sensitivity and successful restore coverage. No scheduler or retention worker is installed here.                            |
| RPO at most 24 hours, RTO at most four hours               | **Proposed targets**, not measured production guarantees. RPO is the accepted data-loss interval to a verified cutoff; RTO includes restore, verification and safe cutover. Measure both against representative data and the actual incident topology.                          |
| Periodic restore exercises and backup-age monitoring       | **Recommended deployment practice.** Assign an owner, schedule, alert destination and pass/fail record. The repository supplies an isolated drill, not hosted monitoring/alert delivery.                                                                                        |

An operator can adopt stricter controls or tighter targets, but must record how the actual deployment meets them. A tiny local drill does not establish production capacity, and [FA-04](../final-audit.md) remains open.

## Assemble the complete recovery set

Before a planned backup, identify the source and record the intended recovery boundary privately. Use the following completeness checklist; it supplements the canonical [recovery-set definition](../backup-and-recovery.md#recovery-set-and-consistency).

| Element                                          | Minimum retained evidence                                                                                                                                                                                                                     | Consequence if absent                                                                                                                                                            |
| ------------------------------------------------ | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PostgreSQL application/auth/queue/migration data | Complete custom-format dump, including immutable financial sources, allocation/revision/audit/outbox history, strategy/journal/import/review data, sequences, functions, owners/grants, forced RLS/policies, constraints and enabled triggers | An application-only export cannot recover complete authentication, queue/security state or original provenance. A projection rebuild does not recreate lost authoritative facts. |
| Global roles and reviewed grants                 | Application role identities/attributes and separately reviewed operator requirements; no runtime memberships that permit `SET ROLE` escalation                                                                                                | `pg_dump` does not include cluster-global roles. Restored owners/ACL/security-definer functions can be wrong or unusable without them.                                           |
| Private media                                    | Coordinated entire `STORAGE_ROOT`, directory/object layout and lifecycle states, plus expected ready-object sizes/SHA-256                                                                                                                     | Database metadata can point to missing/corrupt bytes. Copying only visible current screenshots omits other authorized evidence and lifecycle context.                            |
| Exact application/release                        | Commit, complete source/dependency/build identity, lockfile, runtime/tool versions and reviewed migrations                                                                                                                                    | A different schema/calculation version can produce incompatible or changed results.                                                                                              |
| Protected configuration and secrets              | Recoverable database/runtime credentials, matching auth secret where session restoration is intended, private storage path/ownership, proxy/TLS and encryption-key recovery through a separate secret system                                  | SQL/media do not recreate credentials, certificates or the correct deployment bindings. Restored sessions may fail, or an unintended origin/target may be selected.              |
| Authenticated private manifest                   | Consistency cutoff, source alias, release/schema/calculation context, archive/media sizes/hashes, table/security/financial comparison evidence, backup results and protected copy locations                                                   | A file timestamp does not prove a coherent recovery point, authenticity or successful capture.                                                                                   |

Runtime roles are `journal_app`, `journal_auth` and `journal_jobs`; the non-login `journal_migrator` owns reviewed objects. Runtime roles remain non-owner, `NOINHERIT`, `NOSUPERUSER`, `NOCREATEDB`, `NOCREATEROLE`, `NOBYPASSRLS`, `NOREPLICATION`, with no inherited/`SET ROLE` route through another role. The dedicated migrator's reviewed owner capability must not pass to runtime identities. Source: [role provisioning](../../packages/database/src/migrate.ts), [production preflight](../../scripts/operations/production-preflight.ts) and [recovery role guard](../../scripts/operations/recovery-safety.ts).

Do not publish role files, connection strings or manifests as a support attachment. Password-free role exports still disclose deployment/security information. Keep secret values out of shell arguments/history/logs; the operator template uses private libpq service/password files instead of embedded passwords. Do not copy a production auth secret/session database into a public test environment.

## Take and complete a logical backup

This section is **state-changing**: maintenance stops traffic/processes and capture writes sensitive archives. The database capture reads the source; it is not permission to change ledger facts or delete objects.

1. Confirm the source host/database, private storage, release, authorized operator and backup destination. Review available space/inodes, PostgreSQL 17 client/server compatibility and the complete recovery set. Preserve the last known-good set separately.
2. Announce the actual maintenance window through the deployment's established process. Block new ingress, drain/stop every web and worker replica and external writer, and wait for transactions/uploads to finish. Reads can still write auth/rate-limit state; leaving an apparently read-only web replica running does not establish quiescence.
3. Record the cutoff and source-side exact financial/security/media evidence. Inspect pending/staging lifecycle state without deleting it. A DB-only snapshot cannot atomically freeze filesystem changes.
4. Apply the canonical [backup procedure](../backup-and-recovery.md#backup-procedure) using a new restricted operator-owned directory and explicit source service. Follow its command ordering and stop on every failed exit. Its service/path examples are deployment placeholders, not a provisioned production backup connection.
5. Verify each expected archive is nonempty, listable as appropriate and matches its manifest/hash. Review the role subset privately; a shared-cluster role dump can contain unrelated roles. Retain complete ownership/ACL/security definitions instead of using selective flags to hide failures.
6. Encrypt/authenticate the protected transfer, verify the offsite copy independently and confirm that the recovery team can obtain the keys through a separate channel. SHA-256 alone does not protect against replacement of both data and checksum.
7. Mark the set complete only after the following completion gate passes. Resume the original system under its reviewed release/configuration after the coordinated copies and manifest are complete; record successful service/readiness/attachment checks.

| Backup completion gate     | Required evidence                                                                                                                                                 |
| -------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Capture                    | All individual command exits passed; complete DB/global-role/media components and release/secret-recovery references exist.                                       |
| Consistency                | Recorded quiesced cutoff and writers stopped throughout DB/media capture; source financial/media/security fingerprints retained privately.                        |
| Integrity                  | Recorded artifact sizes/hashes, expected DB contents/owners/ACLs and every ready-media relationship; no omitted collections/files hidden by a success label.      |
| Protected independent copy | Authenticated/encrypted off-host copy and separately recoverable keys/access; a second directory on the same failed host is not independent protection.           |
| Restoration evidence       | Last successful isolated restore's date, release, dataset and result are associated with the set/policy. A newly written set is not automatically restore-tested. |
| Operations                 | Owner, completion/failure time, last-good age and unresolved gaps are recorded. A failed new attempt never replaces the last good set.                            |

If capture fails, preserve the safe error/step and protected artifacts, retain the previous good set, and use [backup troubleshooting](../troubleshooting/backup-and-recovery.md). Do not delete data or raise/remove safety limits to convert a failure into a passing backup.

## Restore a complete system into an isolated target

> **Warning:** Restore changes roles, schemas, rows and files. A later cutover can discard post-cutoff writes or resurrect old access. Preserve a coordinated backup of the current state and authenticate the candidate recovery set before any potentially destructive replacement. Never restore over an existing populated target as an ordinary troubleshooting action.

1. Identify the incident, accepted cutoff/loss interval, matching release and recovery-set provenance. Retain the failed source, volumes, media and safe logs. Separate recovery from an upgrade: first reproduce the backed-up release faithfully.
2. Confirm an empty isolated PostgreSQL 17 target/private media directory and sufficient resources; keep ingress, workers and all other writers stopped. Ensure no process still points to an old/live target or can create split-brain writes.
3. Apply the canonical [restore procedure](../backup-and-recovery.md#restore-procedure). It restores reviewed roles and complete SQL/media with owners/ACLs/constraints intact. Do not run migrations into an empty target before the archive restore; the archive already contains its schema/history. Any later forward upgrade needs its own compatibility review and backup.
4. Complete the independent post-restore checks below before opening ingress. Preserve expected and actual results without stripping decimal precision, economic timestamps, revision/provenance or unavailable/partial states to make equality appear.
5. Resolve revived sessions/memberships and credentials under the incident policy. Matching secrets permit still-valid pre-cutoff sessions; credential/session rotation can invalidate them and must be recorded. The browser portable restore has different access semantics and must not be used as an assumed model for whole-auth-database recovery.
6. Review persisted queue/outbox intent before worker startup. Inspect native source/processed revisions, lease/retry/owner status and guarded current-generation publication using the [outbox reference](../financial-outbox.md). Do not truncate queues, mark intents delivered, manufacture projection results or use a general redrive operation that does not exist.
7. Cut over only after the actual target's operator acceptance, successful authenticated smoke/media checks and resource/readiness checks. Keep the original isolated for investigation, avoid two writable systems, record elapsed restore/verification/cutover and the observed data-loss interval, and establish a new verified backup.

| Post-restore check  | What must agree or remain enforced                                                                                                                                                                                          |
| ------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Release and schema  | Matching original release/calculation context, exact migration history, schema compatibility, reviewed queue schema and no edited applied migration.                                                                        |
| Data and sequences  | Complete canonical table/sequence evidence and immutable financial/source/audit relationships. Rebuilt projections are compared, not substituted for lost originals.                                                        |
| Security            | Role attributes/memberships, owners/grants/default grants, functions/search paths, forced RLS/policies, constraints and triggers; no unexpected privilege or disabled guard. No-context/wrong-tenant access remains denied. |
| Money and inventory | Exact cash, quantities/lots/allocations, realized/unrealized availability, account bridge and selected financial/journal DTOs under the same inputs/version/time policy. Schema readiness alone does not certify them.      |
| Private media       | Expected ready-object count, lifecycle state, size/hash and authorized original-byte retrieval; staging/pending/removed objects are not silently published.                                                                 |
| Authentication      | Expected safe session behavior, fresh sign-in and authorized workspace reads; incident-required revocations/secret changes have the stated effect.                                                                          |
| Worker              | Infrastructure round trip plus separate native-snapshot currentness/retry checks for its declared all-recorded-event scope. Neither probe is a valuation/report completion signal.                                          |
| Actual deployment   | Canonical HTTPS/origin/proxy, private ports, storage persistence/capacity, supervised process drain/start, protected backup access and the approved cutover boundary.                                                       |

Failure at a gate means recovery is incomplete. Keep the target private and collect sanitized evidence; do not bypass constraints/authentication or directly edit authoritative financial facts. Use [diagnostics](../troubleshooting/diagnostics.md) and [financial troubleshooting](../troubleshooting/financial-discrepancies.md) to separate evidence gaps from an actual economic discrepancy.

## Rehearse with the repository's disposable drill

Use the canonical [local drill invocation and prerequisites](../backup-and-recovery.md#reproducible-local-drill), not the production SQL template, to practice safely. The root script is [declared in package.json](../../package.json) and implemented by [recovery-drill.ts](../../scripts/operations/recovery-drill.ts); [CI](../../.github/workflows/ci.yml) invokes it with an isolated project/output. A configured workflow step does not establish a successful hosted run.

The drill creates its own tiny synthetic source database and separate PostgreSQL 17 tmpfs restore container. Its target-ownership guard rejects caller-selected existing targets, its output file must be unused, and its fixture bindings must match the selected local Compose test service. Success removes only the exact resources generated by that invocation and retains private artifacts; failure retains isolated evidence for reviewed cleanup. It never contacts production. Do not weaken the ownership/port/image checks to reuse a real installation as the target.

Its checks include complete database-rendered table/sequence/security fingerprints before restored writes, exact financial DTOs, restricted roles, existing session/fresh login, wrong-tenant denial, attachment bytes/hash and a restored pending infrastructure probe. Numeric hashes retain PostgreSQL-rendered exact values instead of passing authoritative decimals through JavaScript `Number`. A temporary cross-runtime membership negative check occurs only on the newly created target and is revoked before final equality/preflight.

The tiny fixture does not independently restore every populated original-risk/strategy/import/correction/transfer workflow, a native-snapshot generation, a large dataset, offsite/encryption/key recovery, actual production TLS, HA or PITR. Its report's older sentence that end-user workspace export/import is unimplemented is stale product wording: that feature is implemented separately, while this drill does not test its browser archive path. Preserve the report unchanged and record the correct scope beside it. See [current checkpoint verification](verification.md) for executed invocation, tool versions, result, retained failures/corrections, resource cleanup and limits; the [17 October historical timings](../backup-and-recovery.md#verified-evidence-and-remaining-gates) remain historical.

## Retain and review recovery evidence

Keep backup artifacts private, encrypted where required by the selected deployment, authenticated, access-controlled and recoverable independently of the original host. Protect manifest and key access as separate failure/security boundaries. Test that the on-call recovery operator can obtain the approved set and keys without copying credentials into support logs.

The ADR's 30-day retention applies to a proposed backup policy, not permission to delete immutable ledger/source/audit history. Select expiry only after preserving the required successful/restorable recovery chain, legal/business obligations and an independent good copy. No automated backup expiry, orphan cleanup, encryption-key rotation, offsite transfer or alert recipient is installed by these guides. Do not improvise deletion commands against private media or database tables to implement retention.

A useful private completion record identifies source/target aliases, cutoff, backup/recovery release, PostgreSQL/runtime tools, archive/media hashes/sizes, command exits, last-good age, comparisons, observed restoration time, actual loss interval, owner and unresolved gates. The shared support summary should contain only reviewed step/status/request IDs and counts/version findings. Dumps, roles, raw manifests, environment values, session cookies, private paths, financial sources and original media require a separate authorized channel; [diagnostics](../troubleshooting/diagnostics.md) defines sanitization.
