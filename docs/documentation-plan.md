## Cross-document dependencies and acceptance

The preparation order is baseline and environments → clean setup → task walkthroughs → reference reconciliation → operational verification → maintenance/extension → final integration. Architecture/financial verification can run alongside task writing when both use the same pinned source baseline. Operational command verification depends on actual available infrastructure and must report blocked checks without substituting assumptions.

Every later checkpoint must:

- Use the feature inventory to cover all implemented user and API features, including remediation additions and relevant limitations.
- Link requirement IDs and `AC-01`–`AC-16` where financial or acceptance coverage is claimed. A passing smaller workflow must not certify a larger scenario or FA-04.
- Verify referenced source paths, command existence, sample inputs, resulting state and exact financial outputs where relevant.
- Respect existing edits and historical evidence. Scope changes to the canonical document; do not erase old findings, then-current counts or approval history.
- Apply the documentation standards, check local links/anchors and run repository formatting/whitespace checks for changed files.
- Record newly executed checks separately from retained remediation evidence, with command, date, version/commit, environment, outcome and limitations.

## Unresolved questions and retained gates

1. **Checkpoint allocation:** the titles and allocation for Checkpoints 2–7 above are proposed here. Any previously agreed allocation supplied later should be reconciled without duplicating deliverables.
2. **Production capacity:** FA-04 remains open. Which production workload, concurrency, resource and latency acceptance evidence will close it is an engineering/release decision, not a documentation assertion.
3. **Host validation:** actual deployment OS/architecture, reverse proxy/TLS, hosted CI results, monitoring/alerts, offsite backup and production-scale recovery targets still require host-specific evidence. Repository configuration does not prove those environments were exercised.
4. **Advanced native operations:** native derivative/fixed-income lifecycle formulas and additional extension modules retain their documented gates. Explicit reviewed residual/campaign values and manual source recording must be explained accurately without promoting an entire family to native support.
5. **Scope bounds:** imports, synchronous archives, reconciliation, reporting, return-series boundaries, catalogs and worker projections have different limits. Later guides must cite the current operation-specific bounds instead of one generic supported-history claim.
6. **Representative demo:** `db:seed` currently creates a labeled empty demo workspace, not the varied financial dataset required by F-UX-08. Checkpoint 2 must state that initial state; later screenshots require isolated synthetic data rather than a claimed populated demo.
7. **Documentation drift:** remediation refreshed major entry points, while README and older feature/capability references still contain the concrete stale statements listed above. Their existence is tracked work; Checkpoint 1 preserves them for focused reconciliation in later checkpoints.
