# ADR-0007: Private files, PostgreSQL-backed jobs, and verified restore

- **Status:** Proposed
- **Date:** 2026-10-06
- **Requirements:** Specification §4, §10–14; F-AS-01–03, F-IM-01–08, N-IM-01–02, F-IN-02, F-SE-03–04; decisions D-13–17; acceptance scenarios AC-11, AC-14–16.

## Context

The journal requires private screenshots/documents, preserved import files, large imports, filtered exports, recomputation after corrections, and lossless backups with tested restore. HTTP request lifetimes are unsuitable for all of that work. Files cannot be made public because a UI hides their URLs, and a database transaction cannot atomically commit bytes to a filesystem or an object store.

Use one application codebase and PostgreSQL rather than introducing independently deployed business services, Redis, or a required paid storage provider. Long-running work still needs durable execution, bounded resources, authorization, failure visibility, and reproducible results.

## Decision

### Private storage contract

Use a server-side `PrivateFileStore` interface for streaming staged writes, reads, atomic finalization where supported, existence/hash verification, and deletion. Persist logical attachment/source-file records in PostgreSQL: workspace, stable UUID, original display name, private storage locator, declared and detected media type, size, SHA-256, purpose, uploader/provenance, lifecycle status, and linked records. A storage key is opaque, generated by the server, and never a user-supplied path.

The zero-subscription default is a **private local filesystem directory on a persistent volume**, outside the public/static web root. Web and worker processes share that directory with restrictive ownership/permissions. Resolve only server-generated paths, reject symlinks/path traversal, and never mount it as a public web directory. This topology supports one host with multiple local processes; it is not a shared-disk assumption across hosts.

An **S3-compatible private object-store adapter** is the supported alternative for production across hosts. Keep the adapter provider-neutral, use least-privilege credentials and private buckets, and verify complete multipart uploads before activation. No object store, paid provider, or subscription is necessary for core local operation. The initial delivery route is an authorized application stream; a future short-lived object-store download URL would need explicit bounded lifetime, access-policy review, and tests for revocation behavior.

All upload, list, read, attach, detach, delete, source-download, and export-download operations use current workspace authorization from [ADR-0003](0003-authentication-and-tenancy.md). Resolve the file's database record before reading bytes. Do not trust a workspace/file key supplied directly to the storage adapter by a browser or a job payload.

### Validation and safe delivery

Proposed reversible initial limits are **20 MiB per attachment**, **100 MiB per original CSV/JSON import file**, **100,000 rows per source**, and **1 GiB total expanded restore content**. Stream and count bytes/rows; apply request, worker, image-dimension, nesting, field-length, and disk-space limits in addition to header checks. Exceeding a limit returns a useful error rather than attempting an unbounded parse. Archive-entry count and compression-ratio limits must also be explicit in the restore parser tests.

Accept JPEG, PNG, WebP, and PDF for screenshots/reference attachments. Inspect extension, declared MIME, byte signature, and decoder/parser results together; an extension or `Content-Type` alone is insufficient. Do not allow SVG, HTML, JavaScript, arbitrary executables, or archives as ordinary attachments. CSV and the application's validated JSON are source-import types; only the application's defined backup archive format is a restore package.

Keep original accepted source bytes immutable for provenance. Generate bounded raster thumbnails through a vetted decoder rather than embedding original active content. Serve PDFs and original sources as downloads with safe filenames, `Content-Disposition: attachment`, and `X-Content-Type-Options: nosniff`; use a constrained same-origin image preview for validated raster content. Sanitize any rich-text notes with an allowlist, escape ordinary text, and keep download responses outside executable HTML contexts. Antivirus can be an optional adapter, but its absence is never labeled “malware cleared.” Do not treat type validation as a guarantee that every file is harmless.

Filtered CSV exports escape spreadsheet-formula-sensitive cells without changing canonical stored strings. Export templates, quoted cells, leading whitespace/control characters, and imported notes all need injection tests. A backup restores canonical strings, not the spreadsheet-sanitized representation.

### File/database consistency

Represent file lifecycle as staged/quarantined, validating, ready, rejected, and pending deletion rather than assuming successful byte upload implies a visible attachment. The upload path is:

1. Authorize and create a bounded private staging record/path; stream bytes and calculate size/hash.
2. Validate format and purpose; finalize to an immutable private key, verifying the stored bytes/hash. Local finalization uses a same-volume atomic rename; object-store finalization must verify the completed object.
3. In a database transaction, publish a ready file record, its tenant-scoped links, audit event, and any follow-up outbox work. Readers only see ready records.

If storage succeeds but the database transaction fails, the bytes are an orphan pending cleanup. If finalization fails, the database never advertises usable content. Deletion records intent transactionally and removes bytes idempotently after reference/retention checks. Reconcile staged/orphaned objects with a grace period; do not delete a key merely because a transient lookup failed. Mutable storage contents cannot silently replace a ready object's accepted hash.

### Durable jobs in the modular monolith

Use **pg-boss 12.x** backed by PostgreSQL, running a dedicated Node.js worker from the **same repository, application modules, and container image** as the web process. The chosen Node 24/PostgreSQL 17 baseline exceeds the official project's documented Node 22.12/PostgreSQL 13 minimums. Pin the exact queue release and validate its schema/migration and transaction adapter during scaffolding. No Redis or independently versioned business microservice is introduced.

Queue responsibilities include source parsing/dry-run validation, large import orchestration, export/backup assembly, restore validation, expensive valuation/analytics rebuilds, thumbnail generation, and storage cleanup. Small financial commands still validate, lock, post conserved allocations/balanced ledger entries, and record audit history **synchronously in one database transaction**. A queue success message is not a financial posting commit.

Write a durable **application outbox** in the same transaction as the authoritative change or job request. A dispatcher submits referenced tasks to pg-boss and marks delivery; a crash between those actions may resubmit. pg-boss supports transaction-aware enqueueing, but an explicit outbox also makes the business event, required calculation version, source revision, ownership, and audit linkage independently inspectable. Avoid two authoritative job-state models: the application job record is user-visible business progress, pg-boss is transport/execution state, and the outbox is pending delivery.

Design for at-least-once execution even where the queue provides stronger delivery guarantees. A durable idempotency key identifies each business task/version; database constraints and handler checkpoints make repeated submissions/retries safe. Queue messages contain identifiers and revision/version references, not credentials, file contents, journal prose, or whole financial datasets. Only an authenticated persisted job/outbox record can grant task scope.

Use exponential backoff for transient errors, bounded attempts, explicit permanent failures, and failed-job inspection/redrive. Proposed initial worker concurrency is two jobs, with one import/restore financial commit per workspace at a time. Stream/chunk reads, bound memory and temporary disk use, and instrument queue lag, duration, retry count, and resource exhaustion. Cancellation is cooperative between chunks; committed financial work is reversed through domain rules rather than hidden deletion. Handler completion atomically records result/progress where possible; an expired lease or process restart must not duplicate output or financial activity.

User-requested tasks reload initiating membership at start and before delayed financial commit or artifact publication. System projection tasks have a distinct narrow service capability derived from a trusted committed event. The worker obtains a fresh tenant transaction context and never uses a migration/superuser role to bypass ownership. Queue-schema grants do not grant authentication-table access or unrestricted tenant mutations.

### Projection revision and consistency

Each workspace/account authoritative financial change advances a revision within its transaction. Projection work records input revision, calculation version, observation/FX selection versions, and output definition. Compute against a consistent snapshot, write into staging/versioned projection rows, and activate only with a compare-and-swap against the revision intended for publication. A superseded job cannot overwrite current totals.

Until a rebuild succeeds, APIs return an explicit pending/stale/unavailable result with its revision and last successful calculation metadata; they do not label old numbers current. Queries that require current financial invariants use authoritative records or synchronous projections, never a stale cache. Corrections invalidate affected dependencies and coalesce rebuild work without losing audit history. Matching calculation versions and canonical inputs must reproduce totals deterministically.

### Backup and restore contract

Use a versioned, documented **application JSON manifest plus a media package**. Plain JSON contains lossless domain data and manifest references; a complete workspace backup packages that JSON together with original import/source files and attachment bytes. It is incomplete if a referenced file is missing. The package manifest records format version, database/domain schema version, calculation versions, workspace reporting/time settings, source financial revision, each file's logical ID/type/size/SHA-256, and integrity information for canonical JSON data.

Include authoritative records, historical metadata/strategy/risk/plan versions, observations, source rows/mappings, imports, corrections, audit provenance, and selected preferences/settings. Preserve exact decimal strings, timestamp/source-timezone fields, missingness/provenance, and historical FX/calculation references. Derived data may be retained for comparison but is rebuilt and verified before restore activation. Exclude authentication identities/credential accounts, sessions, password/verification secrets, memberships/permissions, queue leases, deployment credentials, and live provider tokens. Keep historical actor provenance as non-authenticating audit identifiers/labels; it never creates access rights.

Backups use a consistent PostgreSQL snapshot at a declared revision and immutable file hashes, so editing activity during assembly cannot produce a mixed snapshot. Include a compatibility report: restoring financial totals requires the matching calculation versions or an explicitly reviewed migration/recalculation; never silently use a new formula and claim identical restoration.

Restore **only into a newly created empty workspace namespace**, initially owned by the authenticated restoring owner. Remap the workspace namespace while preserving stable tenant-local domain IDs and all domain relationships. Rebind active ownership to the restoring owner; retain imported actor/source provenance separately. No merge/overwrite restore into an existing populated workspace is provided initially. This boundary avoids destructive replacement and ambiguous collision/correction semantics.

Before committing, stage and verify the entire manifest and every file; reject absolute/traversal paths, duplicate entries/IDs, links, decompression bombs, oversized/nested content, unknown required versions, hash mismatches, missing references, cross-workspace links, or unsupported formats. Show a dry-run summary. Load bounded staged rows into an inaccessible draft workspace, apply schema/capability validation, rebuild with the declared calculation versions, and compare record counts/invariants/totals. Activate the workspace only after verification succeeds. Failed/canceled restore is visibly failed and cleans up private staging; it never publishes a partially restored workspace.

Workspace exports are portability artifacts, not substitutes for operational PostgreSQL plus private-file backups. Deployment documentation must define coordinated DB/file snapshots, encryption/access controls, retention, and restore drills. Proposed single-instance operational targets are a daily backup (up to 24-hour recovery point) and a tested four-hour recovery time, subject to representative-volume restore measurement; they are goals, not claims of an existing service guarantee.

## Alternatives considered

- **Public object URLs or public static directories:** easy image delivery but violate private ownership and revocation requirements.
- **Database byte columns for every file:** one transaction/backup boundary but increases primary database size and operational cost for media. Keep metadata/lineage in PostgreSQL and bytes in a private adapter.
- **Required cloud object storage:** useful for shared deployment, but unnecessary external dependency for a locally runnable core. Offer it as an adapter.
- **In-process fire-and-forget tasks:** lose progress on restart and cannot safely handle retries/imports. Use persisted task state and a worker.
- **Redis queue or separate import service:** adds a second operational data store/service without current scale justification. PostgreSQL-backed jobs share existing operations.
- **Synchronous HTTP for all bulk work:** simpler only for small files; request timeouts and partial failure become ambiguous for large imports/backups.
- **Restore by merging into arbitrary existing workspaces:** would require product decisions about conflicts, financial reversals, IDs, permissions, and history. New empty namespace is the safe initial contract.

## Consequences

Local operation needs persistent PostgreSQL and file volumes plus a web and worker process. Cross-host scaling requires shared object storage, while queued work can scale within explicit per-workspace concurrency constraints. Operations must monitor free disk, abandoned jobs/files, queue migrations, integrity failures, and backup freshness.

Outbox/worker/projection machinery adds justified complexity but keeps financial invariants in synchronous domain transactions. Recovery is explicit and testable rather than relying on a queue's delivery slogan. Changing storage providers does not change domain entities; changing calculation versions requires a compatibility/recompute path. Backup artifacts contain sensitive financial/journal information and need the same privacy discipline as live records.

## Validation required before accepting implementation

- Exercise both local storage and an S3-compatible test adapter with unauthorized reads, guessed IDs, traversal/symlinks, malformed MIME, active content, size/dimension limits, orphan cleanup, and interrupted multipart finalization (AC-14).
- Kill/restart a worker before/after enqueue, file finalization, financial commit, and acknowledgement; duplicate delivery must change no balances/counts and must not publish duplicate artifacts (AC-11, AC-16).
- Verify job membership removal, bounded retries, cancellation, per-workspace commit serialization, and absence of secrets/source contents in queue/logging DTOs.
- Race an old projection job with a correction/new revision: old output cannot replace current totals; pending/stale state remains visible until the matching rebuild completes.
- Restore representative multi-currency, partial-fill, metadata/version, unknown-basis, import-correction, and attachment data into a new workspace. Compare authoritative counts, relationships, SHA-256 hashes, audit/source provenance, and derived totals under identical calculation versions (AC-15).
- Reject corrupted/incomplete archives, hostile paths/links, unsupported versions, collision/merge attempts, and decompression/row-limit violations. Confirm failed restore has no visible partial workspace.
- Run an operational DB/file recovery drill against measured backup volume before claiming recovery targets or supported production readiness.
