# Configuration

Use this reference when preparing a local source checkout or diagnosing a configuration rejection. It covers the bindings actually read by the application, its launchers, Compose and repository tools. Toolchain and platform compatibility belong to the [system requirements](system-requirements.md) and [environment inventory](../environment-inventory.md); production host procedures belong to [deployment](../deployment.md).

## Configuration precedence

For the root launchers and database/operator tools, [loadEnvironment](../../scripts/environment.ts) reads the repository-root `.env` through dotenv. An existing process environment value takes precedence over `.env`; the loader does not use `override: true`. Parser defaults apply only when a declared optional value is absent. An empty or invalid value is not a request to generate a replacement secret.

The [local initializer](../../scripts/env-init.ts), exposed as the `env:init` package script, creates `.env` with exclusive creation and mode `0600`, generates random credentials for the administrator and three runtime roles, and creates `.private/storage` with mode `0700`. Generated development/test instances use matching per-role passwords but different database targets. If `.env` exists, it preserves the file. It does not merge settings, repair credentials or update an existing database. Its success message identifies creation or preservation without printing values. Follow [installation](installation.md) for the verified command sequence.

Only these initializer inputs can be overridden in its process environment: `APP_ORIGIN`, `WEB_HOST`, `POSTGRES_PORT`, `TEST_POSTGRES_PORT`, `WORKER_HEALTH_HOST`, `WORKER_HEALTH_PORT` and `COMPOSE_PROJECT_NAME`. It derives `PORT` from the chosen origin and writes `NODE_ENV=development`, `LOG_LEVEL=info` and `STORAGE_ROOT=.private/storage`. Other inherited values do not customize those generated fields. The initializer validates its inputs before checking whether `.env` exists, so an invalid inherited origin or port can still fail a preservation attempt.

> **Important:** `.env.example` is a tracked template with unusable secret placeholders. Copying its password or auth-secret placeholders does not produce a working configuration. Use generated private values; do not post `.env`, database URLs, passwords or session cookies in logs or support requests.

The actual template is [.env.example](../../.env.example), and [.gitignore](../../.gitignore) excludes private environment files, storage and scratch outputs. Keep `.env` private even though Git ignores it. Standard root scripts deliberately load that file; they do not implement a selectable `--env-file` option or an application-specific `.env.local` precedence chain. Avoid invoking workspace processes directly and relying on a different current directory or framework environment-file discovery.

The [launchers](../../scripts/processes.ts) filter child environments. Web receives its declared runtime bindings; worker receives only its queue and operational bindings. Neither receives migration, administrator, bootstrap, test or unrelated provider credentials. System/tool variables are preserved only through the explicit allowlist. This filtering does not make it safe to publish the parent environment.

## Runtime bindings

**Restart rule:** restart every affected running service after changing a runtime binding. The server configuration and logger are cached; database pools, authentication and worker listeners are initialized for the process. Editing `.env` does not reload them. Restarting applies configuration but does not migrate data, rotate PostgreSQL credentials or move attachments.

The tables use **required** to describe the consumer, **default** for an actual parser/template value, and angle-bracket text for a private placeholder that must be replaced. Examples are shapes, not usable credentials.

## Production boundary

Set `NODE_ENV=production`, a canonical HTTPS `APP_ORIGIN`, explicit private listener/port settings and an absolute persistent `STORAGE_ROOT` for the production service. Supply the distinct `DATABASE_URL`, `AUTH_DATABASE_URL` and `JOB_DATABASE_URL` targets and a strong stable `BETTER_AUTH_SECRET` through the approved service-manager/secret-store environment. Keep all three runtime database roles on the intended migrated PostgreSQL 17 database. Configure verified database TLS through the PostgreSQL connection/trust settings appropriate to the host; the application does not provision certificates or validate a remote deployment by parsing a URL.

Keep repository `.env` development/test bindings out of the production artifact. Use the migration operator binding only for explicit one-shot tooling, and keep `BOOTSTRAP_PASSWORD` out of long-running services. Restart the affected services after a coordinated change. Neither `start` nor `start:web` changes these bindings into production values; an HTTPS origin also does not create a TLS listener. Follow the separately scoped [production source installation](installation.md#production-source-installation). Actual-host TLS/session/storage/recovery/capacity remains **Not run** in this checkpoint.

## Diagnosing configuration failures

The server parser reports `ServerConfigurationError` and field names, not secret values. Worker startup reports `INVALID_WORKER_CONFIGURATION` with invalid field names. A PostgreSQL connection failure or schema mismatch can occur after syntactic validation succeeds. Compare the reported field with the appropriate table; share only the field/error classification and sanitized results.

- A rejected `APP_ORIGIN` usually means a remote development/test host, production HTTP, embedded credentials or an added path/query/fragment. Keep the browser URL, origin and listener port consistent.
- Missing runtime URL fields are not repaired by supplying `MIGRATION_DATABASE_URL`. Web requires all three runtime URLs; worker needs its queue URL only.
- A valid new `.env` does not update an existing PostgreSQL volume's passwords. Preserve the existing private configuration and database; investigate which identity/target failed before changing credentials.
- A rejected storage path or permission is a private-media safety boundary. Use an operator-controlled private directory, not a public/static/build directory or symlink.
- A port conflict requires selecting an unused local port and updating its dependent configuration consistently; changing only `APP_ORIGIN`, `PORT` or a Compose port is insufficient.

Existing regression evidence for these boundaries is in [server configuration tests](../../tests/unit/server-config.test.ts), [worker configuration tests](../../tests/unit/worker-config.test.ts), [process/environment tests](../../tests/unit/process-environment.test.ts) and [test database binding tests](../../tests/unit/test-database-config.test.ts). [Verification](verification.md) records what was freshly executed for Checkpoint 2. Configuration checks do not close FA-04, certify a deployment or enable unavailable integrations.
