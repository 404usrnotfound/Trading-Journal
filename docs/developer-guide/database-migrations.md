This is a developer guide to persistence changes and database tests. The [architecture](../architecture.md), [ADR 0006](../decisions/0006-postgres-drizzle-and-migrations.md) and [domain model](../domain-model.md) retain their authoritative design roles; actual schema/runtime files below establish the implemented boundary.

The journal's internal format version `7` is not the application schema version. [Operations verification](../operations/verification.md) records the prior isolated migration/recovery checks and the **failed seven-advisory dependency audit**; that failure and [FA-04](../final-audit.md) are not closed by a database test or documentation change.

## Persistence ownership

| PostgreSQL schema | Responsibility                                                                                                                            | Developer boundary                                                                                                                                           |
| ----------------- | ----------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `app`             | Workspaces/membership, financial source facts/postings, versions, journal/strategy/import/review data, audit and controlled derived state | Tenant data uses composite workspace identities, current membership and forced RLS. Source/history and controlled projections have different mutation rules. |
| `auth`            | Global Better Auth identity/session/password/throttling models and narrow authentication-security audit                                   | Authentication rows are not tenant financial records or public DTOs. Keep credentials, hashes and session tokens out of exports and logs.                    |
| `queue`           | pg-boss tables and the explicitly granted native-outbox functions                                                                         | Queue migration is an operator phase. Runtime jobs do not receive general tenant/auth access or arbitrary DDL/function execution.                            |
| `migrations`      | Drizzle application migration ledger `__drizzle_migrations`                                                                               | Applied history is evidence. Do not edit it to make a release compatible.                                                                                    |

The [schema composition](../../packages/database/src/schema.ts) creates `databaseSchema` for typed Drizzle access and re-exports table definitions through `@journal/database/schema`. The [database package manifest](../../packages/database/package.json) exports the pool/transaction API at `@journal/database` and tooling at `@journal/database/migrate`. Drizzle declarations describe typed columns and relationships; reviewed SQL additionally owns policies, grants, functions, generated-value guards, deferred triggers and cross-row invariants that a TypeScript model alone cannot establish.

The [database-management guide](../operations/database-management.md) owns the complete role/migration inventory and operator maintenance boundaries. Do not copy its deployment/restore procedure into a feature migration.

## Database module interfaces

### Connections and authorized transactions

Source: [database entry point](../../packages/database/src/index.ts).

| Field                    | Contract                                                                                                                                                                                                                                        |
| ------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Purpose                  | Provide one owned PostgreSQL pool and typed Drizzle database, with transaction-scoped actor/workspace context.                                                                                                                                  |
| Responsibilities         | Validate context shape, set transaction-local `app.user_id`/`app.workspace_id`, release context on commit/rollback, expose workspace bootstrap/query helpers and close owned connections.                                                       |
| Dependencies             | node-postgres `Pool`, Drizzle SQL/transactions, `databaseSchema` and reviewed PostgreSQL RLS/privileged functions. No React or HTTP dependency.                                                                                                 |
| Public interfaces        | `createDatabase`, `Database`, `DbTransaction`, `TenantContext`, `TenantTransactionOptions`, `withActorTransaction`, `withTenantTransaction`, `listOwnWorkspaces`, `createPersonalWorkspace`, `ensurePersonalWorkspace`; re-exported `eq`/`sql`. |
| Relevant tests           | [Database integration](../../tests/integration/database.test.ts), [idle-error unit tests](../../tests/unit/database-idle-errors.test.ts), plus feature-specific restricted-role suites below.                                                   |
| Extension considerations | Add server-authorized data access inside the correct transaction; do not accept actor identity from a browser body or use a shared operator connection as a runtime shortcut. Close fixture pools before removing only their owned resources.   |

`createDatabase(url, {max?})` returns `{pool, db, close}`. Default pools have ten connections, five-second connection timeout, thirty-second idle timeout and ten-second statement timeout. These are implementation defaults, not newly exposed tuning environment variables. The safe idle-client error listener emits only `database.idle-connection-failed`; active query errors still reject. Do not log raw driver exceptions, connection objects, SQL parameters or URLs.

`withTenantTransaction(database, verifiedContext, callback, options)` sets actor and UUIDv4 workspace context **locally inside that transaction**. The actor is a nonempty bounded server-verified identity; auth actor IDs are not required to use the financial UUID format. Options support `read committed`, `repeatable read` or `serializable`, and `read only`/`read write`. Multi-query reports choose their reviewed consistent-snapshot policy; do not collect half a report outside that transaction.

`withActorTransaction` has actor context without selected tenant context for narrow own-workspace/bootstrap operations. It is not a replacement for workspace authorization. `ensurePersonalWorkspace` is operator bootstrap/seed infrastructure: it serializes by verified creator/environment and reuses only a workspace still owned and created by that actor. It does not authenticate a password or make someone else's membership a personal workspace.

RLS combines the transaction context with **current** membership. Composite `(workspace_id, id)` references prevent linking a valid object to a different workspace. Context-free or wrong-workspace tenant queries deny/return no authorized rows; pooled or nested transactions must not inherit another request's identity. Server action authorization, session and Origin/CSRF checks remain mandatory because a compromised SQL-capable server can forge context. Never disable RLS in a test to simulate a successful ordinary request.

## Financial persistence invariants

Financial stored values use canonical text and generated `NUMERIC(78,36)` columns through `app.financial_decimal`. SQL checks the lexical/envelope constraints **before** the numeric cast, so PostgreSQL coercion cannot silently round rejected excess precision. Do not switch codecs to JavaScript `number`, insert generated numeric columns directly, merge incompatible units or use display rounding as source data. Keep exact economic timestamps/source ordering separate from recording time and financial revision.

Append-only source executions/openings/cash/FX/fees, balanced postings, published versions and audit/command results are distinct from controlled rebuildable inventory/pointers. Deferred SQL checks independently enforce per-currency balancing, source cash/quantity/cost conservation, version references, command effects and workspace ownership. The server commits the source, revision, inventory effect, stored idempotent result, audit and outbox intent in the same appropriate financial transaction. A failed deferred check rolls back that command; a manual balancing row is not a migration remedy.

Use the existing [financial SQL](../../packages/database/migrations/0002_core_financial_ledger.sql), [ledger reference](../core-ledger.md) and [financial definitions](../financial-metrics.md) rather than duplicating formulas here. Readiness or schema presence is not evidence that every native instrument operation is supported.

## Author a forward migration

The [journal](../../packages/database/migrations/meta/_journal.json) currently contains seventeen published SQL files, `0000`–`0016`. The [database inventory](../operations/database-management.md#review-schema-and-migration-history) maps each to its purpose/schema version. Published SQL and historical snapshots are evidence; add a new reviewed migration rather than editing an applied file.

1. Define the intended invariant and data transition first. Inspect the affected Drizzle model, contracts, services, historical fixture population, grants/RLS and archive/worker implications. Identify incompatible existing data and the supported response; do not silently rewrite immutable financial or audit history.
2. Update the relevant model definitions and schema composition/export where needed. Keep type-safe application access consistent with the actual SQL; model presence alone does not create a database object.
3. Prepare a **new candidate** additive SQL migration in a separate working branch/directory, then review its full effect. The [Drizzle config](../../packages/database/drizzle.config.ts) selects PostgreSQL, `src/schema.ts`, `migrations`, and `app`/`auth` for **candidate generation only**. It is not a runtime migration command or complete representation of custom SQL invariants.
4. Check generation metadata before relying on a diff. The tracked `meta` snapshots stop at `0007_snapshot.json`, while published SQL/journal continues through `0016`. No root/package `db:generate` or migration-generation script exists; the database package exposes only `typecheck`. This guide therefore does not invent a generation invocation or claim a verified end-to-end generator workflow. Do not regenerate/overwrite old snapshots or interpret an incomplete candidate as permission to remove later objects. Any tooling/metadata repair needs a separate reviewed, rehearsed change.
5. Add the new reviewed SQL and its new journal entry together. The [release checker](../../scripts/release-check.ts) requires contiguous journal indices, unique four-digit/name tags, strictly increasing safe-integer timestamps and exact equality between SQL files and journal entries. Keep historical ordering/timestamps intact. A proposed future filename such as `0017_<reviewed_name>.sql` is a placeholder, not an existing migration or command.
6. Review explicit owners, grants/default grants, forced RLS/policies, pinned `SECURITY DEFINER` search paths, triggers/deferred constraints, indexes and data transformations. Account for pg-boss and any narrow worker function grants separately. Never grant broad tenant SQL to the jobs role to simplify a feature.
7. Advance the schema marker and the intended release's `DATABASE_SCHEMA_VERSION` together when extending this schema chain; add fixtures for compatibility and rejected/failed transitions. The current constant is 17, not a blanket acceptance of future versions. Update relevant release/archive/calculation compatibility checks deliberately rather than disabling them.
8. Validate empty installation, populated prefix upgrade and failure behavior on newly isolated databases, including old rows/permissions and every affected financial/domain condition. Keep a recoverable original set before a potentially destructive real release. Record the exact source, fixture, commands and outcomes.

Drizzle Kit is pinned as a package development dependency, but no new source-generation command is promised here. Do not use schema `push`, an unreviewed live diff, application startup DDL or manual journal/hash edits against shared data. The [ADR](../decisions/0006-postgres-drizzle-and-migrations.md) requires reviewed SQL beyond generated candidates; its initial “not implemented” context is historical, not a claim that today's persistence is absent.

## Execute and inspect migrations

All commands below run from the **repository root** with the [supported toolchain/configuration](../getting-started/configuration.md), installed full dependencies and the explicitly intended database. Existing environment values take precedence over the repository `.env`. These commands are **Source-reviewed**; consult [developer verification](verification.md) for current execution and [operations verification](../operations/verification.md) for historical local results.

| Command                          | Effects, prerequisites and expected result                                                                                                                                                                                                                                                                                                 |
| -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| `corepack pnpm db:migrate`       | **State-changing** one-shot operator command. Needs `MIGRATION_DATABASE_URL` plus the three private runtime URLs for password/grant provisioning. Applies reviewed application SQL, pg-boss schema/queue setup, then all three runtime roles. Success: `Database and queue migrations applied; least-privilege runtime roles provisioned.` |
| `corepack pnpm db:check`         | **Read-only** application-role connectivity/schema/major check using `DATABASE_URL`. Success: `Runtime application role connects successfully; database schema is current.` It does not compare every migration hash, inspect all role grants or verify private media.                                                                     |
| `corepack pnpm db:migrate:check` | **State-changing disposable-test** command. Uses guarded `TEST_DATABASE_URL`, calls the application migrator twice and verifies schema. Success: `Isolated test database migrations and repeatability checks passed.` It does not itself call queue migration or runtime-role provisioning.                                                |
| `corepack pnpm test:integration` | **State-changing disposable-test** suite. Its global setup validates all four test bindings, applies application/queue migrations and provisions runtime roles before fixtures. Runs real PostgreSQL transaction/constraint/RLS/migration checks.                                                                                          |

The [application runner](../../packages/database/src/migrate.ts) permits PostgreSQL 17, acquires advisory lock `1791244800` with a thirty-second lock timeout, checks existing history is an exact reviewed hash/timestamp/order prefix, applies SQL and checks schema. Existing-history verification occurs under that application migration lock. [Readiness](../../packages/database/src/readiness.ts) is deliberately separate and imports no DDL tooling.

The root [migration script](../../scripts/migrate.ts) runs application migration, [worker queue migration](../../apps/worker/src/migrate.ts) and role provisioning **as separate phases**. The application lock ends before the later phases, and their full sequence is not a global atomic transaction. Serialize the complete release job. Runtime workers set `migrate: false` through their reviewed queue factory and must not create/upgrade queue schemas independently.

`provisionRuntimeRoles` reapplies configured passwords and the explicit role/queue grants; it is not a harmless status check or single-password rotation tool. It does not by itself prove an externally modified role has no replication privilege, memberships or ownership. The [role/preflight and credential guidance](../operations/database-management.md#maintain-separate-operator-and-runtime-identities) owns those checks. Keep operator credentials out of web/worker runtime environments.

For exact **read-only** schema/history inspection use [the diagnostics probe](../troubleshooting/diagnostics.md#inspect-migration-state). On failure preserve the sanitized code and original state; CLI tools intentionally omit raw driver details. Follow [database troubleshooting](../troubleshooting/database-and-migrations.md) and the [upgrade decision procedure](../operations/upgrades-and-rollback.md), not ad hoc DDL or repeated new release attempts.

## Test databases and fixtures

Follow [installation](../getting-started/installation.md) and [test binding configuration](../getting-started/configuration.md#isolated-test-bindings) before running mutation-capable tests. The local [Compose file](../../compose.yaml) supplies separate `postgres` and `postgres-test` services; development data uses a named volume while test data uses tmpfs. Confirm that the actual target is disposable rather than relying on a database name alone.

The [binding validator](../../scripts/environment.ts) requires all four `TEST_DATABASE_URL`, `TEST_APP_DATABASE_URL`, `TEST_AUTH_DATABASE_URL` and `TEST_JOB_DATABASE_URL` values to use PostgreSQL URLs with explicit user/password, no query/fragment, the same host/port/database and a database name ending `_test`. Loopback aliases compare as one host. The target must differ from **every** configured development/operator database. Those guards do not make a real user's similarly named database disposable.

[Integration global setup](../../tests/integration/global-setup.ts) uses the test operator for schema/queue migration and extracts passwords from the three test runtime URLs for provisioning. Tests then use actual non-owner runtime identities, generated actor/workspace IDs and explicit cleanup predicates. Migration fixtures additionally create uniquely named temporary `_test` databases on the dedicated instance; the test operator needs `CREATEDB` for that path. Never repoint tests at a shared/user database, truncate broad tables, substitute SQLite or use superuser results as proof of runtime authorization.

The [database integration suite](../../tests/integration/database.test.ts) covers empty creation, original-platform upgrades preserving users/sessions/workspaces/preferences/audit/permissions, exact repeat/concurrent history, rejected changed/missing/duplicate/unknown history, context/tenant isolation and atomic failed application upgrades. Journal/accounting/financial suites add their populated-prefix and direct-constraint cases. Add a failing regression fixture independent of the changed implementation, then exercise new constraints through both authorized services and direct restricted SQL as appropriate. Testing an injected bad journal row is safe only in an invocation-owned fixture; it is never a repair instruction for real history.

## Seed behavior and rollback limits

The supported seed command is:

```bash
corepack pnpm db:seed --email owner@example.test
```

This fictional address must resolve to an **existing provisioned owner** in the selected local installation. Run from repository root with the configured app/auth bindings. It is **state-changing** workspace setup and is **Source-reviewed**, not an executed seed claim for this document. The [seed script](../../scripts/seed.ts) looks up the existing auth identity and calls `seedDemoWorkspace`; it ensures a separately labeled **empty demo workspace**. It does not create that owner, download data, seed varied trades/currencies/instruments or fund an account. Its success message is `Demo workspace is ready. It is labeled and empty; no financial records were seeded.` Verify the intended owner/workspace and empty financial state before using it. Normal bootstrap is documented in [first run](../getting-started/first-run.md).

There is no down-migration script or generic database downgrade procedure. A runtime requiring schema 17 rejects an incompatible schema even if tables look familiar. A failed application SQL upgrade can roll back its own transaction, as the migration tests demonstrate; that does not roll back completed queue/provisioning phases or later committed financial writes. Older-code reversion requires explicit persisted/schema compatibility. Full recovery uses the matching release and verified coordinated database/media/secrets set into a new empty target, with an acknowledged cutoff/loss interval. [Operations](../operations/upgrades-and-rollback.md) owns that decision; volume deletion, metadata rewrites and historical financial edits are not developer rollback techniques.
